**Nguyên tắc chung cho mọi module:**
- **Contract-first**: mỗi module expose interface rõ ràng, không phụ thuộc implementation.
- **Stateless by default**: trạng thái lưu ở DB/cache bên ngoài.
- **Idempotent**: mọi operation có thể retry an toàn.
- **Multi-tenant aware**: mọi call mang theo `TenantId`.
- **Observable**: mỗi module phát ra metric, log, trace.
- **Testable**: 100% unit test cho business logic, integration test cho IO.

## 2. Layer 3: AI Provider Abstraction

Layer này là "bí mật cốt lõi" của platform - cho phép chuyển đổi giữa các AI provider mà không ảnh hưởng đến tầng trên. Toàn bộ các module khác chỉ phụ thuộc vào abstraction, không bao giờ gọi trực tiếp OpenAI/Anthropic API.

### 2.1 LLM Provider Module

**Mục đích**: Chuẩn hóa việc gọi LLM (Chat Completion + Streaming) từ nhiều nhà cung cấp (OpenAI, Anthropic, Ollama, Azure OpenAI, DeepSeek, Groq, Gemini, OpenRouter) về một contract duy nhất.

**Kiến trúc nội bộ**:

```
┌──────────────────────────────────────────────────────────┐
│               ILLMProvider (interface)                    │
│  ChatAsync / StreamChatAsync / GetModelInfo              │
└──────────────┬───────────────────────────────────────────┘
               │ (implements)
   ┌───────────┼────────────┬─────────────┬───────────────┐
   ▼           ▼            ▼             ▼               ▼
┌──────┐  ┌──────┐    ┌────────┐    ┌────────┐       ┌────────┐
│Ollama│  │OpenAI│    │Anthropic│   │ Azure  │  ...  │Groq    │
│Prov. │  │Prov. │    │Provider │   │OpenAI  │       │Provider│
└──────┘  └──────┘    └────────┘    └────────┘       └────────┘
   │           │            │             │               │
   └───────────┴────────────┴─────────────┴───────────────┘
                                  │
                                  ▼
                        ┌──────────────────────┐
                        │ ProviderRouter       │
                        │ (chọn provider tối ưu)│
                        └──────────────────────┘
```

**Interface (C# mẫu)**:

```csharp
public interface ILLMProvider
{
    string ProviderId { get; }                 // "openai", "ollama", ...
    Task<ChatResponse> ChatAsync(ChatRequest request, CancellationToken ct);
    IAsyncEnumerable<ChatDelta> StreamChatAsync(ChatRequest request, CancellationToken ct);
    ModelCapabilities GetCapabilities(string modelId);
    Task<HealthStatus> HealthCheckAsync(CancellationToken ct);
}

public record ChatRequest(
    string ModelId,
    IList<ChatMessage> Messages,
    double Temperature = 0.7,
    int? MaxTokens = null,
    IReadOnlyDictionary<string, object>? Tools = null,
    ToolChoice? ToolChoice = null,
    Guid TenantId = default,
    string? TraceId = null
);

public record ChatResponse(
    string Content,
    string? FinishReason,
    UsageInfo Usage,                          // prompt/completion/total tokens
    IReadOnlyList<ToolCall>? ToolCalls,
    string ProviderId,
    string ModelId,
    TimeSpan Latency
);
```

**Data Model**:

- `ProviderConfig`: cấu hình provider trong DB (ApiKey, BaseUrl, Enabled, RateLimit).
- `ModelCatalog`: danh sách model mà provider hỗ trợ.
- `ChatMessage`: chuẩn hóa message (System/User/Assistant/Tool) cho mọi provider.

**Luồng hoạt động** (Chat Completion):

1. Caller gửi `ChatRequest` qua `ProviderRouter`.
2. Router chọn provider (xem 2.3) → trả về `ILLMProvider` cụ thể.
3. Provider map `ChatRequest` sang payload riêng (OpenAI format, Anthropic format...).
4. Gọi HTTP API với retry + circuit breaker.
5. Map response về `ChatResponse` chuẩn.
6. Ghi metric: latency, token usage, error rate.

**Điểm tích hợp**:
- Được gọi bởi: RAG Engine, Agent Executor, Voice Engine (TTS prompt), SQL Engine.
- Phụ thuộc: Provider Cache, Model Registry, Provider Router.

**Xử lý lỗi**:
- `ProviderUnavailableException` → router failover.
- `RateLimitExceededException` → exponential backoff + jitter.
- `InvalidRequestException` → trả về caller (không retry).
- `ContextLengthExceededException` → tự động tóm tắt lịch sử (gọi chính nó) hoặc trả lỗi.

**Testing**:
- Unit test từng provider với mock HTTP server (WireMock.Net).
- Contract test: response từ mọi provider phải map đúng `ChatResponse`.
- Chaos test: giả lập provider down → router phải chuyển sang provider khác.

### 2.2 Embedding Provider Module

**Mục đích**: Chuẩn hóa việc tạo vector embedding từ text. Tách biệt với LLM Provider vì embedding model thường khác LLM model (và có thể dùng provider khác nhau).

**Interface**:

```csharp
public interface IEmbeddingProvider
{
    string ProviderId { get; }
    int Dimensions { get; }                                    // 768, 1536, 3072...
    Task<EmbedResponse> EmbedAsync(EmbedRequest request, CancellationToken ct);
    Task<IReadOnlyList<EmbedResponse>> BatchEmbedAsync(BatchEmbedRequest req, CancellationToken ct);
}

public record EmbedRequest(string ModelId, string Text, Guid TenantId);
public record EmbedResponse(float[] Vector, string ModelId, int TokensUsed);
```

**Đặc tả quan trọng**:
- Bắt buộc hỗ trợ **batch embedding** (gộp nhiều text trong 1 request) để tối ưu chi phí.
- Cache theo hash(text) để tránh embed lại nội dung trùng.
- Chuẩn hóa `Dimensions` theo từng model (rất quan trọng với pgvector).

**Điểm tích hợp**:
- Được gọi bởi: Document Ingestion, Hybrid Search (rerank score), Memory Manager.

### 2.3 Provider Router & Failover

**Mục đích**: Chọn provider tối ưu theo **cost / latency / quality / availability**. Đây là "bộ não" của Provider Abstraction.

**Kiến trúc nội bộ**:

```
┌────────────────────────────────────────────────────────────┐
│                    ProviderRouter                           │
│                                                             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────────┐  │
│  │ Health       │  │ Cost/Latency │  │ Tenant Preference │  │
│  │ Monitor      │  │ Statistics   │  │ (config)          │  │
│  └──────┬───────┘  └──────┬───────┘  └────────┬─────────┘  │
│         │                 │                   │             │
│         └─────────────────┼───────────────────┘             │
│                           ▼                                 │
│                  ┌──────────────────┐                       │
│                  │ Selection Policy │                       │
│                  │ • cost-first     │                       │
│                  │ • latency-first  │                       │
│                  │ • quality-first  │                       │
│                  │ • fallback       │                       │
│                  └──────────────────┘                       │
└────────────────────────────────────────────────────────────┘
```

**Các chiến lược chọn provider (Selection Policy)**:

| Strategy | Logic | Use case |
|----------|-------|----------|
| `CheapestFirst` | Ưu tiên provider có $/token thấp nhất | Batch processing, dev |
| `FastestFirst` | Ưu tiên provider có P95 latency thấp nhất | Real-time chat |
| `QualityFirst` | Ưu tiên provider có benchmark cao nhất | Critical task |
| `RoundRobin` | Phân phối đều | Load balancing |
| `TenantPinned` | Tenant chỉ định provider cụ thể | Enterprise yêu cầu compliance |

**Failover logic**:
1. Provider chính fail (timeout, 5xx) → chuyển sang provider phụ theo danh sách ưu tiên.
2. Circuit Breaker: sau N lỗi liên tiếp → mở circuit, không gọi provider đó trong 60s.
3. Health check chạy nền mỗi 30s → cập nhật `ProviderHealth`.
4. Tất cả failover được log + emit event `ProviderFailoverTriggered`.

**Cấu hình failover chain (ví dụ trong DB)**:

```json
{
  "tenantId": "...",
  "primaryProvider": "openai",
  "primaryModel": "gpt-4o",
  "fallbackChain": [
    { "provider": "anthropic", "model": "claude-3-5-sonnet" },
    { "provider": "ollama",    "model": "llama3.2:70b" }
  ],
  "maxRetries": 2,
  "retryDelayMs": 500
}
```

**Interface**:

```csharp
public interface IProviderRouter
{
    Task<ILLMProvider> SelectLLMProviderAsync(ProviderSelectionContext ctx, CancellationToken ct);
    Task<IEmbeddingProvider> SelectEmbeddingProviderAsync(ProviderSelectionContext ctx, CancellationToken ct);
}

public record ProviderSelectionContext(
    Guid TenantId,
    string? PreferredProvider = null,
    string? RequiredCapability = null,         // "vision", "function-call", "json-mode"
    RoutingStrategy Strategy = RoutingStrategy.CostFirst,
    int? MaxLatencyMs = null
);
```

### 2.4 Provider Cache

**Mục đích**: Cache response của LLM/Embedding để giảm chi phí và tăng tốc độ.

**Hai loại cache**:

1. **Exact-match cache**: key = hash(prompt + model + temperature + params).
   - Dùng cho: system prompt lặp lại, FAQ bot, test.
2. **Semantic cache**: key = embedding của prompt.
   - Dùng cho: câu hỏi tương tự nhau nhưng khác wording.

**Kiến trúc**:

```
Request → [Semantic Similarity Check] → Cache Hit? → Return cached
                │
                └─→ Cache Miss → Call Provider → Store result → Return
```

**Cấu hình**:
- TTL: mặc định 24h cho exact, 1h cho semantic.
- Threshold similarity: 0.95 cho semantic (rất cao để tránh sai).
- Storage: Redis (exact) + pgvector (semantic).
- Tenant-scoped: cache riêng cho mỗi tenant.

**Interface**:

```csharp
public interface IProviderCache
{
    Task<T?> GetAsync<T>(string cacheKey, CancellationToken ct) where T : class;
    Task SetAsync<T>(string cacheKey, T value, TimeSpan ttl, CancellationToken ct) where T : class;
    Task<T?> GetSemanticAsync<T>(string prompt, float[] embedding, double threshold, CancellationToken ct) where T : class;
    Task InvalidateTenantAsync(Guid tenantId, CancellationToken ct);
}
```

### 2.5 Model Registry

**Mục đích**: Lưu trữ metadata của tất cả model AI mà platform hỗ trợ, cung cấp khả năng "khám phá" model theo capability.

**Data Model**:

```sql
CREATE TABLE model_registry (
    id              UUID PRIMARY KEY,
    provider_id     VARCHAR(50) NOT NULL,         -- "openai", "ollama"
    model_id        VARCHAR(100) NOT NULL,        -- "gpt-4o", "llama3.2:3b"
    display_name    VARCHAR(200),
    type            VARCHAR(20) NOT NULL,         -- "chat" | "embedding" | "rerank"
    context_window  INT NOT NULL,
    input_cost      DECIMAL(10, 6),               -- $/1k tokens
    output_cost     DECIMAL(10, 6),
    dimensions      INT,                          -- for embedding
    capabilities    JSONB,                        -- ["vision", "function-call", "json-mode"]
    enabled         BOOLEAN DEFAULT true,
    metadata        JSONB,
    created_at      TIMESTAMPTZ DEFAULT now(),
    UNIQUE(provider_id, model_id)
);
```

**API của Registry**:
- `ListModelsAsync(filter)` - lọc theo capability, type, cost.
- `GetModelAsync(providerId, modelId)`.
- `RegisterModelAsync(...)` - thêm model mới.
- `SyncFromProviderAsync(providerId)` - đồng bộ model list từ provider API.

**Điểm tích hợp**: Provider Router query registry để biết provider nào có model "vision".

## 3. Layer 4: AI Engine Core

Đây là "trái tim" của platform, chứa toàn bộ khả năng AI cốt lõi.

### 3.1 RAG Engine

**Mục đích**: Kết hợp **Retrieval** (tìm kiếm tài liệu liên quan) với **Generation** (sinh câu trả lời từ LLM dựa trên ngữ cảnh tìm được). Đây là tính năng được dùng nhiều nhất.

**Kiến trúc nội bộ**:

```
User Query
   │
   ▼
┌──────────────────┐
│ Query Rewriter   │  - Mở rộng query (HyDE, multi-query)
│                  │  - Phát hiện ngôn ngữ
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ Retriever        │  - Vector search
│                  │  - Hybrid search
│                  │  - Filter theo metadata
└────────┬─────────┘
         │
         ▼ (top-k chunks)
┌──────────────────┐
│ Reranker         │  - Sắp xếp lại theo relevance
│                  │  - Loại bỏ noise
└────────┬─────────┘
         │
         ▼ (top-n most relevant)
┌──────────────────┐
│ Context Builder  │  - Sắp xếp chunks
│                  │  - Cắt/truncate theo context window
│                  │  - Thêm system prompt
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ LLM Generation   │  - Sinh câu trả lời
│                  │  - Streaming
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ Post-Processor   │  - Trích citation
│                  │  - Validate output
│                  │  - PII masking
└────────┬─────────┘
         │
         ▼
RAG Response (answer + sources + metadata)
```

**Interface chính**:

```csharp
public interface IRAGEngine
{
    Task<RAGResponse> QueryAsync(RAGQuery query, CancellationToken ct);
    IAsyncEnumerable<RAGDelta> StreamQueryAsync(RAGQuery query, CancellationToken ct);
}

public record RAGQuery(
    string Query,
    Guid TenantId,
    string? CollectionId = null,            // collection tài liệu
    IReadOnlyList<string>? DocumentIds = null,
    int TopK = 10,
    int TopN = 5,                           // sau rerank
    double MinRelevanceScore = 0.5,
    RAGStrategy Strategy = RAGStrategy.Hybrid,
    ChatMessage[]? ConversationHistory = null,
    IDictionary<string, object>? Filters = null
);

public record RAGResponse(
    string Answer,
    IReadOnlyList<Citation> Citations,      // nguồn trích dẫn
    RAGMetrics Metrics                      // latency, tokens, retrieval score
);
```

**Các chiến lược RAG (Strategy enum)**:

| Strategy | Mô tả |
|----------|-------|
| `Vector` | Chỉ tìm vector |
| `Keyword` | Chỉ tìm keyword (BM25) |
| `Hybrid` | Kết hợp vector + keyword (RRF) |
| `HyDE` | Hypothetical Document Embedding - sinh câu trả lời giả trước, tìm theo đó |
| `MultiQuery` | Sinh N query variants, tìm trên tất cả, merge |
| `StepBack` | Trừu tượng hóa query thành câu hỏi tổng quát hơn |
| `SelfRAG` | LLM tự đánh giá retrieval có đủ không, nếu không thì tìm lại |

**Data Model**:

- `rag_collections`: nhóm tài liệu (per tenant).
- `rag_documents`: metadata tài liệu.
- `rag_chunks`: nội dung đã chunk.
- `rag_embeddings`: vector của chunks.
- `rag_query_logs`: lịch sử query (cho analytics).
- `rag_feedback`: user feedback (like/dislike) để fine-tune.

**Luồng chi tiết (1 request)**:

1. **Authentication**: lấy `TenantId` từ JWT.
2. **Query Rewriting**: tùy strategy, có thể gọi LLM 1 lần để expand query.
3. **Embedding**: gọi Embedding Provider.
4. **Retrieval**: gọi Vector Store + (optional) Full-Text Search → lấy top-k candidates.
5. **Reranking**: gọi Reranker model (Cohere Rerank hoặc local cross-encoder).
6. **Context Building**: ghép top-n chunks vào prompt, cắt nếu vượt context window.
7. **Generation**: gọi LLM Provider, có thể streaming.
8. **Post-processing**: trích citation, validate, log.
9. **Response**: trả về answer + citations + metrics.

**Điểm tích hợp**:
- Phụ thuộc: Document Ingestion (để có data), Vector Store, Embedding Provider, LLM Provider, Citation Engine.
- Được gọi bởi: API Gateway (chat endpoint), Agent Orchestration.

**Xử lý lỗi**:
- Không tìm thấy tài liệu liên quan → trả "Tôi không tìm thấy thông tin phù hợp" (không hallucinate).
- LLM timeout → trả lỗi 504 với suggestion retry.
- Reranker fail → fallback về top-k theo vector score.

**Testing**:
- Unit test: query rewriter, context builder, citation extractor.
- Integration test: end-to-end với sample documents.
- Evaluation: chạy RAGAS / DeepEval để đo context precision, faithfulness.

### 3.2 Document Ingestion & Chunking

**Mục đích**: Nhận tài liệu từ nhiều nguồn (upload, URL, connector), parse, chunk, embed và lưu vào Vector Store.

**Pipeline chi tiết**:

```
Input Document
   │
   ▼
┌──────────────────┐
│ Format Detector  │ - Detect MIME type
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ Document Parser  │ - PDF, DOCX, TXT, MD, HTML, CSV
│                  │ - OCR cho ảnh scan
│                  │ - Trích bảng, ảnh, code block
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ Cleaner          │ - Loại bỏ header/footer lặp
│                  │ - Chuẩn hóa whitespace
│                  │ - Loại bỏ boilerplate
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ Chunker          │ - Tách thành chunks
│                  │ - Giữ overlap để không mất ngữ cảnh
│                  │ - Gắn metadata
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ Enricher         │ - Sinh summary cho mỗi chunk (optional)
│                  │ - Trích entities (optional)
│                  │ - Gán tags
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ Embedder         │ - Batch embedding
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ Indexer          │ - Lưu vào Vector Store + Metadata DB
└────────┬─────────┘
         │
         ▼
Done (phát event DocumentIndexed)
```

**Các chiến lược Chunking**:

| Strategy | Mô tả | Use case |
|----------|-------|----------|
| `FixedSize` | Chia chunk theo số token cố định (vd 512 tokens) | Text thuần, đơn giản |
| `Recursive` | Chia theo cấu trúc (`\n\n` → `\n` → `. ` → ` `) | Văn bản tổng quát |
| `Semantic` | Embed từng câu, gộp các câu có similarity cao | Tài liệu phức tạp |
| `Document` | Theo cấu trúc tài liệu (heading, section) | Markdown, HTML |
| `Markdown` | Theo header/section của Markdown | Tài liệu kỹ thuật |
| `Code` | Theo function/class | Source code |
| `SlidingWindow` | Overlap cố định giữa các chunks | Khi cần ngữ cảnh liên tục |

**Config mặc định**:
- Chunk size: 512 tokens
- Overlap: 50 tokens
- Splitter: Recursive

**Data Model**:

```sql
CREATE TABLE rag_documents (
    id              UUID PRIMARY KEY,
    tenant_id       UUID NOT NULL,
    collection_id   UUID,
    source          VARCHAR(50),        -- "upload", "url", "connector:erp"
    source_uri      TEXT,
    title           VARCHAR(500),
    mime_type       VARCHAR(100),
    size_bytes      BIGINT,
    status          VARCHAR(20),        -- "pending", "processing", "ready", "failed"
    error_message   TEXT,
    metadata        JSONB,
    created_at      TIMESTAMPTZ,
    indexed_at      TIMESTAMPTZ
);

CREATE TABLE rag_chunks (
    id              UUID PRIMARY KEY,
    document_id     UUID REFERENCES rag_documents(id) ON DELETE CASCADE,
    chunk_index     INT,
    content         TEXT NOT NULL,
    token_count     INT,
    metadata        JSONB,              -- heading, page_number, ...
    created_at      TIMESTAMPTZ
);

CREATE TABLE rag_embeddings (
    chunk_id        UUID PRIMARY KEY REFERENCES rag_chunks(id) ON DELETE CASCADE,
    embedding       VECTOR(1536),       -- pgvector
    model_id        VARCHAR(100),
    embedded_at     TIMESTAMPTZ
);

-- Index cho vector search
CREATE INDEX ON rag_embeddings USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);
```

**Interface**:

```csharp
public interface IDocumentIngestionService
```

**Xử lý lỗi**:
- Parser fail → status="failed", lưu error_message, gửi notification.
- Embedding provider down → retry với backoff, sau N lần thất bại → fail cả job.
- Vector store down → lưu vào outbox table, xử lý lại sau.

**Async processing**:

- Worker (background job) xử lý parse → chunk → embed → index.
- Phát event `DocumentIndexed` qua Event Bus.
- Frontend poll progress qua SignalR/WebSocket.

### 3.3 Vector Store & Semantic Search

**Mục đích**: Lưu trữ và tìm kiếm vector embedding với hiệu năng cao. Hỗ trợ nhiều backend (pgvector, Qdrant, Weaviate, Pinecone, Milvus).

**Interface (abstraction)**:

```csharp

    Guid Id,
    float Score,
    string Content,
    IReadOnlyDictionary<string, object>? Metadata
```

**Backend mặc định**: PostgreSQL + pgvector.

**Lý do chọn pgvector cho phiên bản đầu**:
- Không thêm hạ tầng mới (đã có PostgreSQL).
- Hỗ trợ hybrid: vector + full-text + structured query trong cùng 1 SQL.
- ACID transaction với metadata.
- Chi phí thấp.

**Khi nào chuyển sang Qdrant/Milvus**:
- Quy mô > 10M vectors.
- Cần filtering phức tạp với tốc độ cao.
- Cần multi-tenant ở mức collection.

**Index strategy**:
- < 1M vectors: `ivfflat` với `lists=100`.
- 1M - 10M: `hnsw` với `m=16, ef_construction=64`.
- > 10M: chuyển sang Qdrant/Milvus.

**Cấu hình tenant isolation**:
- Mỗi tenant có `collectionId` riêng → cách ly vật lý.
- Hoặc dùng RLS: mọi query filter theo `tenant_id`.

### 3.4 Hybrid Search & Reranker

**Mục đích**: Kết hợp nhiều phương pháp tìm kiếm để tăng độ chính xác.

**Kiến trúc**:

```
Query
   │
   ├──► Vector Search ─────┐
   │                        │
   ├──► BM25 (Full-Text) ──┼──► Fusion (RRF) ──► Reranker ──► Top-N
   │                        │        ▲
   └──► Metadata Filter ───┘        │
                                    │
                          Reciprocal Rank Fusion
                          score(d) = Σ 1 / (k + rank_i(d))
```

**Các thuật toán fusion**:

| Algorithm | Mô tả |
|-----------|-------|
| RRF (Reciprocal Rank Fusion) | Đơn giản, hiệu quả, dùng rank |
| Linear Combination | `α * vector_score + β * keyword_score` (cần normalize) |
| Cross-Encoder Rerank | Model riêng (Cohere Rerank, BGE-reranker) đánh giá lại cặp (query, doc) |

**Config**:

```json
{
  "hybrid": {
    "vectorWeight": 0.7,
    "keywordWeight": 0.3,
    "rrfK": 60,
    "topK": 20,
    "reranker": {
      "enabled": true,
      "model": "cohere-rerank-3",
      "topN": 5
    }
  }
}
```

**Interface**:

```csharp
public interface IHybridSearchService

}

public record HybridSearchRequest(
```

### 3.5 Citation Engine

**Mục đích**: Trích xuất và định dạng citation (trích dẫn nguồn) cho câu trả lời RAG. Đảm bảo mọi phát biểu của LLM đều có nguồn, chống hallucination.

**Cơ chế**:

1. **Inline citation**: LLM được prompt yêu cầu sử dụng `[1]`, `[2]` trong câu trả lời → ánh xạ sang document.
2. **Post-hoc citation**: Sau khi LLM sinh câu trả lời, dùng embedding similarity để tìm source cho mỗi câu.
3. **Token-level attribution**: Track xem token nào được sinh từ context nào (advanced, cần logprob).

```csharp
    double RelevanceScore
);
```

### 3.6 Tool Engine & Registry

**Mục đích**: Cho phép LLM gọi **function/tool** (function calling). Đây là nền tảng của AI Agent.

**Kiến trúc**:

```
┌────────────────────────────────────────────────────────┐
│                  ToolRegistry                          │
│                                                         │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐ │
│  │ Built-in     │  │ MCP          │  │ User-defined │ │
│  │ Tools        │  │ Tools        │  │ Tools        │ │
│  │ (search, sql)│  │ (external)   │  │ (plugin)     │ │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘ │
│         │                 │                 │          │
│         └─────────────────┼─────────────────┘          │
│                           ▼                            │
│                  ┌──────────────────┐                  │
│                  │ Tool Executor    │                  │
│                  │ - Validate args  │                  │
│                  │ - Permission ck  │                  │
│                  │ - Sandbox        │                  │
│                  │ - Timeout        │                  │
│                  └──────────────────┘                  │
└────────────────────────────────────────────────────────┘
```

**Định nghĩa Tool (theo JSON Schema, tương thích OpenAI Function Calling)**:

```json
{
  "name": "search_documents",
  "description": "Tìm kiếm tài liệu trong knowledge base. Trả về các đoạn text liên quan nhất.",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "Câu truy vấn tìm kiếm"
      },
      "top_k": {
        "type": "integer",
        "description": "Số kết quả trả về",
        "default": 5,
        "minimum": 1,
        "maximum": 20
      },
      "filters": {
        "type": "object",
        "description": "Bộ lọc metadata (ví dụ: {\"department\": \"HR\"})"
      }
    },
    "required": ["query"]
  }
}
```

**Lifecycle của một tool call**:

1. Agent gửi danh sách tools + user prompt cho LLM.
2. LLM quyết định gọi tool nào → trả về `tool_calls`.
3. Agent nhận `tool_calls`, look up tool trong registry.
4. **Validate**: kiểm tra quyền (RBAC), scope (tenant), schema.
5. **Execute**: gọi tool với timeout, sandbox, retry.
6. **Result**: trả kết quả cho LLM để sinh câu trả lời cuối.
7. **Audit**: ghi log tool call (ai gọi, lúc nào, kết quả).

**Built-in Tools mặc định**:
- `search_documents` - RAG search.
- `execute_sql` - Text-to-SQL (cần permission).
- `send_email` - Gửi email (cần approval).
- `create_ticket` - Tạo ticket trong hệ thống ngoài.
- `web_search` - Tìm kiếm web.
- `calculator` - Tính toán chính xác.
- `get_current_time` - Lấy thời gian hiện tại.
- `image_generation` - Sinh ảnh.

**Security**:
- Mỗi tool có `RequiredPermissions` (ví dụ `["erp:read:sales"]`).
- Mỗi tool có `RequiresApproval` flag (tool nguy hiểm cần HITL).
- Sandbox execution: tool user-defined chạy trong container riêng với resource limit.

### 3.7 Workflow Engine

**Mục đích**: Điều phối **workflow nhiều bước** phức tạp: sequence, parallel, conditional, loop, human-in-the-loop. Tương tự Temporal / Airflow nhưng hướng AI Agent.

**Use case**:
- "Phân tích báo cáo Q3 → tóm tắt → gửi email cho sếp" (3 bước).
- "Tìm khách hàng VIP chưa liên hệ 30 ngày → gọi điện → ghi log CRM" (parallel + action).
- "Duyệt đơn nghỉ phép: kiểm tra balance → check overlap → manager approve" (conditional + HITL).

**Định nghĩa workflow (DAG)**:

```json
{
  "name": "phân tích báo cáo quý",
  "steps": [
    {
      "id": "fetch_report",
      "type": "tool",
      "tool": "execute_sql",
      "params": { "query": "SELECT * FROM reports WHERE quarter = :q" }
    },
    {
      "id": "analyze",
      "type": "agent",
      "prompt": "Phân tích báo cáo sau và đưa ra insights chính: {{fetch_report.result}}",
      "dependsOn": ["fetch_report"]
    },
    {
      "id": "send_email",
      "type": "tool",
      "tool": "send_email",
      "params": {
        "to": "manager@company.com",
        "subject": "Phân tích báo cáo quý",
        "body": "{{analyze.output}}"
      },
      "dependsOn": ["analyze"],
      "requiresApproval": true
    }
  ]
}
```

**Step types**:
- `tool` - gọi tool.
- `agent` - gọi LLM (có thể streaming).
- `human` - chờ human input/approval.
- `parallel` - chạy nhiều bước song song.
- `conditional` - if/else.
- `loop` - lặp đến khi điều kiện đạt.

**State management**:
- Workflow state lưu trong DB (PostgreSQL) với status: pending, running, paused, completed, failed.
- Mỗi step có input/output riêng.
- Resume được từ step bị fail.

### 3.8 SQL Engine (Text-to-SQL)

**Mục đích**: Cho phép người dùng hỏi bằng ngôn ngữ tự nhiên và nhận kết quả từ database. Đây là "biên giới" giữa AI và dữ liệu doanh nghiệp, cần bảo mật cao.

**Pipeline**:

```
User Question (NL)
   │
   ▼
┌──────────────────┐
│ Schema Retriever │ - Lấy relevant tables/columns
│                  │ - Embed schema, tìm tables liên quan
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ SQL Generator    │ - Prompt LLM với schema + question
│                  │ - LLM sinh SQL
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ SQL Validator    │ - Parse SQL (AST)
│                  │ - Kiểm tra: chỉ SELECT, không DROP/DELETE/UPDATE
│                  │ - Kiểm tra: có LIMIT, không có full table scan
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ Query Executor   │ - Chạy trên read-only DB user
│                  │ - Timeout, row limit
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ Result Formatter │ - LLM tóm tắt kết quả thành NL
│                  │ - Sinh chart suggestion (optional)
└────────┬─────────┘
         │
         ▼
NL Answer + Data + Optional Chart
```

**Security (rất quan trọng)**:
- Chỉ cho phép `SELECT` (cấm INSERT, UPDATE, DELETE, DROP, ALTER).
- Bắt buộc có `LIMIT` (mặc định 1000 rows).
- Dùng **read-only DB user** với quyền hạn chế.
- Áp dụng row-level security (RLS) theo tenant.
- Whitelist/blacklist tables theo tenant config.
- Tất cả SQL được log để audit.
- HITL bắt buộc cho query "expensive" (estimated cost > threshold).

### 3.10 Memory Manager

**Mục đích**: Quản lý bộ nhớ hội thoại (short-term) và bộ nhớ dài hạn (long-term) cho AI Agent.

**Hai loại memory**:

1. **Short-term (Working memory)**:
   - Lưu trong Redis với TTL (mặc định 24h).
   - Chứa: lịch sử tin nhắn, biến tạm, context của session hiện tại.
   - Sliding window: chỉ giữ N tin nhắn gần nhất.

2. **Long-term memory**:
   - Lưu trong Vector Store.
   - Chứa: thông tin user (preferences, history), facts đã học, summary của conversation cũ.
   - Retrieval: tìm memory liên quan dựa trên query hiện tại.

**Data Model**:

```sql
CREATE TABLE conversation_sessions (
    id              UUID PRIMARY KEY,
    tenant_id       UUID NOT NULL,
    user_id         UUID NOT NULL,
    title           VARCHAR(500),
    metadata        JSONB,
    created_at      TIMESTAMPTZ,
    last_active_at  TIMESTAMPTZ
);

CREATE TABLE conversation_messages (
    id              UUID PRIMARY KEY,
    session_id      UUID REFERENCES conversation_sessions(id) ON DELETE CASCADE,
    role            VARCHAR(20),         -- "user", "assistant", "system", "tool"
    content         TEXT,
    tool_calls      JSONB,
    metadata        JSONB,
    created_at      TIMESTAMPTZ
);

CREATE TABLE user_memories (
    id              UUID PRIMARY KEY,
    tenant_id       UUID,
    user_id         UUID,
    type            VARCHAR(50),         -- "preference", "fact", "summary"
    content         TEXT,
    embedding       VECTOR(1536),
    importance      FLOAT,               -- 0-1
    last_accessed   TIMESTAMPTZ,
    access_count    INT DEFAULT 0
);
```

**Memory retrieval flow** (khi bắt đầu 1 turn mới):

1. Lấy short-term: N tin nhắn gần nhất trong session.
2. Query long-term: embed câu hỏi hiện tại → tìm top-k memories liên quan.
3. Ghép thành context: `[system prompt] + [long-term memories] + [short-term messages] + [current question]`.

**Memory writing flow** (sau mỗi turn):

1. Phát hiện "memory-worthy" info (preference, fact, important decision).
2. Sinh embedding.
3. Lưu vào `user_memories`.
4. Đánh trọng số importance (LLM tự đánh giá hoặc rule-based).

### 4.2 Task Planner

**Mục đích**: Khi nhận task phức tạp, LLM lập kế hoạch (plan) gồm nhiều bước để giải quyết. Đây là core của Agent.

**Các thuật toán planning**:

1. **Plan-and-Execute**:
   - LLM sinh full plan trước, rồi execute từng bước.
   - Ưu: dễ debug, user có thể xem/edit plan trước khi chạy.
   - Nhược: không thích nghi với thông tin mới.

2. **ReAct (Reason + Act)**:
   - Lặp lại: Thought → Action → Observation.
   - Ưu: thích nghi, xử lý được task không lường trước.
   - Nhược: nhiều LLM call, đắt.

3. **ReWOO (Reasoning WithOut Observation)**:
   - Lên plan + dự đoán output của từng bước → giảm số LLM call.
   - Ưu: nhanh, rẻ.
   - Nhược: nếu dự đoán sai thì fail.

4. **Reflexion**:
   - Plan → Execute → Self-critique → Replan.
   - Ưu: chất lượng cao.
   - Nhược: chậm.

**Default strategy**: **Plan-and-Execute + Replan on failure** (cân bằng giữa speed và quality).

### 4.3 Agent Executor

**Mục đích**: Thực thi plan đã được tạo, quản lý vòng đời của từng step, xử lý lỗi, retry, replan.

**State machine của một step**:

```
PENDING
   │
   ▼ (executor chọn step ready)
RUNNING
   │
   ├── success ──► DONE
   │
   ├── fail (retry) ──► RUNNING (loop)
   │
   ├── fail (no retry) ──► FAILED
   │
   ├── needs approval ──► AWAITING_HUMAN ──► (approved) RUNNING / (rejected) CANCELLED
   │
   └── needs replan ──► REPLAN_REQUESTED
```

**Concurrency**:
- Steps không phụ thuộc nhau chạy song song.
- Phụ thuộc chạy tuần tự theo DAG.
- Giới hạn số step chạy đồng thời (vd max 5).

**Error handling**:
- Tool call fail: retry với exponential backoff (max 3 lần).
- Step fail: trigger replan với failure context.
- Replan fail: escalate to human.
- Timeout toàn plan: 5 phút (có thể cấu hình).

**Real-time updates**:
- Mỗi step transition phát event qua Event Bus.
- Frontend subscribe qua SignalR để hiển thị progress.
- User có thể pause/resume/cancel plan đang chạy.

### 4.4 Human-in-the-Loop (HITL)

**Mục đích**: Cho phép con người phê duyệt, sửa, hoặc cung cấp input giữa chừng trong quá trình Agent thực thi. Bắt buộc cho các action nguy hiểm.

**Các loại HITL**:

| Loại | Trigger | Mô tả |
|------|---------|-------|
| **Approval** | Tool có `RequiresApproval = true` | User bấm "Approve" hoặc "Reject" |
| **Input** | Agent cần thông tin user chưa cung cấp | "Bạn muốn nghỉ từ ngày nào?" |
| **Selection** | Có nhiều option hợp lệ | User chọn 1 trong N |
| **Review** | Output có confidence thấp | User xác nhận lại |

**UI Flow**:

```
Agent đang chạy → gặp HITL checkpoint
   │
   ▼
Gửi notification cho user (in-app, email, Slack)
   │
   ▼
User mở HITL interface → xem context → quyết định
   │
   ├── Approve ──► Agent tiếp tục
   ├── Reject ──► Plan bị cancel hoặc replan
   ├── Edit ──► User sửa tham số → Agent tiếp tục với tham số mới
   └── Defer ──► Plan tạm pause, user quay lại sau
```

**Persistence**:
- HITL request lưu trong DB với TTL (mặc định 7 ngày).
- Sau TTL mà chưa được xử lý → auto-cancel plan + thông báo.
- Tất cả quyết định HITL được audit log.

### 4.5 Safety Guardrails

**Mục đích**: Bảo vệ platform khỏi prompt injection, đảm bảo output an toàn, chống data leakage.

**Các lớp guardrails**:

```
┌────────────────────────────────────────────────────────────┐
│                    SAFETY GUARDRAILS                         │
│                                                             │
│  ┌──────────────────────────────────────────────────────┐  │
│  │  INPUT LAYER                                          │  │
│  │  - PII Detection & Masking (email, sđt, CMND)        │  │
│  │  - Prompt Injection Detection                         │  │
│  │  - Toxic Content Detection                            │  │
│  │  - Topic Restriction (whitelist/blacklist)            │  │
│  │  - Length Limit (input token cap)                    │  │
│  └──────────────────────────────────────────────────────┘  │
│                          │                                  │
│                          ▼                                  │
│  ┌──────────────────────────────────────────────────────┐  │
│  │  PROCESSING LAYER                                     │  │
│  │  - Tool Call Validation (schema, permission)         │  │
│  │  - SQL Injection Prevention (parameterized query)    │  │
│  │  - Action Restriction (read-only by default)         │  │
│  │  - Rate Limiting (per user, per tool)                │  │
│  │  - Budget Control (token spend cap)                  │  │
│  └──────────────────────────────────────────────────────┘  │
│                          │                                  │
│                          ▼                                  │
│  ┌──────────────────────────────────────────────────────┐  │
│  │  OUTPUT LAYER                                         │  │
│  │  - Hallucination Detection (citation check)          │  │
│  │  - PII Leakage Detection                              │  │
│  │  - Toxic Output Filter                                │  │
│  │  - Topic Compliance Check                             │  │
│  │  - Output Length Limit                                │  │
│  └──────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────┘
```

**Các kỹ thuật phát hiện**:

1. **Prompt Injection**: dùng LLM riêng (smaller model) để phân loại input có chứa injection không. Hoặc dùng pattern matching cho các câu lệnh phổ biến ("ignore previous instructions", "reveal system prompt").

2. **PII Detection**: regex + Named Entity Recognition (NER) model. Mask trước khi gửi cho LLM (nếu không cần), restore sau khi nhận response.

3. **Hallucination**: kiểm tra citation có tồn tại trong context không, dùng model NLI (Natural Language Inference) để xác nhận câu trả lời có được suy ra từ context không.

4. **Toxic Content**: sử dụng moderation API (OpenAI Moderation, Perspective API) hoặc local classifier.

## 5. Layer 6: AI Gateway

AI Gateway là "cổng vào" của platform, xử lý mọi request từ bên ngoài (UI, API clients, external systems).

### 5.1 Authentication & Authorization

**Mục đích**: Xác thực danh tính (AuthN) và phân quyền (AuthZ) cho mọi request.

**AuthN strategies**:
- **JWT Bearer Token**: dùng cho user/web app.
- **API Key**: dùng cho service-to-service.
- **OAuth2/OIDC**: tích hợp SSO (Azure AD, Google, Okta).
- **mTLS**: cho hệ thống on-premise yêu cầu bảo mật cao.

**AuthZ model**: **RBAC + ABAC kết hợp**.
- **RBAC**: role → permission (vd `admin` có tất cả, `user` có quyền chat).
- **ABAC**: dựa trên attribute (vd chỉ truy cập doc của tenant mình, trong giờ làm việc).

**Permission matrix mẫu**:

| Role | Chat | RAG | Agent | Tool Execution | Admin | Audit |
|------|------|-----|-------|----------------|-------|-------|
| `super_admin` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| `tenant_admin` | ✓ | ✓ | ✓ | ✓ | ✓ (own tenant) | ✓ (own tenant) |
| `power_user` | ✓ | ✓ | ✓ | ✓ (allowed tools) | ✗ | ✗ |
| `user` | ✓ | ✓ | ✓ (pre-approved tools) | ✗ | ✗ | ✗ |
| `guest` | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ |

### 5.2 Rate Limiter

**Mục đích**: Bảo vệ platform khỏi abuse, đảm bảo fair usage giữa các user/tenant.

**Các loại rate limit** (multi-tier):

| Tier | Scope | Algorithm | Mục đích |
|------|-------|-----------|----------|
| L1 - Global | Toàn platform | Token bucket | Chống DDoS |
| L2 - Tenant | Per tenant | Sliding window | Tenant quota |
| L3 - User | Per user | Token bucket | Chống abuse |
| L4 - Endpoint | Per endpoint | Fixed window | Bảo vệ resource đắt |
| L5 - Cost | Per tenant (token spend) | Counter | Kiểm soát chi phí |

**Config mẫu** (per tenant):

```json
{
  "rateLimits": {
    "global": { "requestsPerMinute": 10000 },
    "tenant": { "requestsPerMinute": 1000, "tokensPerDay": 1000000 },
    "user": { "requestsPerMinute": 60, "tokensPerHour": 100000 },
    "endpoints": {
      "POST /api/v1/chat": { "requestsPerMinute": 30 },
      "POST /api/v1/agent/run": { "requestsPerHour": 100 }
    }
  }
}
```

**Storage**: Redis với Lua script cho atomic check.

**Response khi bị limit**:
- HTTP 429 Too Many Requests.
- Header: `Retry-After`, `X-RateLimit-Limit`, `X-RateLimit-Remaining`.
- Body: thông báo lịch sự + suggestion upgrade plan.

### 5.3 Load Balancer & Routing

**Mục đích**: Phân phối request đến backend instances phù hợp, hỗ trợ canary deployment, blue-green.

**Strategies**:

| Strategy | Logic | Use case |
|----------|-------|----------|
| `RoundRobin` | Phân phối đều | Stateless, simple |
| `LeastConnections` | Chọn instance ít connection nhất | Long connection |
| `Weighted` | Phân theo tỉ trọng | Canary, A/B test |
| `IPHash` | Hash(IP) → instance | Sticky session |
| `TenantAware` | Cùng tenant → cùng instance | Cache locality |

**Routing rules**:
- Path-based: `/api/v1/chat/*` → ChatService.
- Header-based: `X-Tenant-Tier: enterprise` → PremiumService.
- Weight-based: 95% traffic → v1, 5% → v2 (canary).

**Health check**:
- Active: GET `/health` mỗi 10s, fail → mark unhealthy.
- Passive: theo dõi 5xx rate, > 50% trong 1 phút → mark unhealthy.
- Auto-remove unhealthy instance khỏi rotation.

### 5.5 Analytics & Observability

**Mục đích**: Cung cấp khả năng quan sát platform end-to-end.

- Provider unavailable > 1 phút → fallback notification.

**MCP Server (phía platform)**:
- Expose các tool của platform (RAG, SQL, custom tools) dưới dạng MCP endpoints.
- Cho phép client MCP (Claude Desktop, các AI client khác) kết nối và sử dụng.

**MCP Client (phía platform)**:
- Platform gọi MCP servers bên ngoài để mở rộng khả năng (ví dụ kết nối GitHub MCP, file system MCP).

**Giao thức MCP (tóm tắt)**:
- Transport: stdio, HTTP+SSE, WebSocket.
- Message format: JSON-RPC 2.0.
- Methods: `initialize`, `tools/list`, `tools/call`, `resources/list`, `resources/read`, `prompts/list`, `prompts/get`.

**Tool definition trong MCP**:
```json
{
  "name": "search_documents",
  "description": "Tìm kiếm tài liệu trong knowledge base",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "top_k": { "type": "integer", "default": 5 }
    },
    "required": ["query"]
  }
}
```

```
┌──────────────────┐         MCP (JSON-RPC)        ┌──────────────────┐
│   MCP Client     │◄─────────────────────────────►│   MCP Server     │
```

### 6.4 Message Queue Adapter

**Mục đích**: Xử lý async task, event-driven workflow, decoupling giữa services.

**Backends hỗ trợ**:
- **RabbitMQ**: development, đơn giản.
- **Apache Kafka**: production, high throughput.
- **Redis Streams**: lightweight option.

**Use case chính**:

| Use case | Queue/Topic | Consumer |
|----------|-------------|----------|
| Document indexing | `document.ingest` | Indexer worker |
| RAG feedback | `rag.feedback` | Analytics collector |
| Email/Slack notification | `notification.outbound` | Notification worker |
| Webhook delivery | `webhook.outbound` | Webhook worker |
| Long-running tool | `tool.long_running` | Tool executor worker |
| Audit log shipping | `audit.log` | SIEM/Archive |
| Reindex tenant | `tenant.reindex` | Reindex worker |
| Agent step execution | `agent.step` | Agent executor worker |

**Message format** (CloudEvents spec):

```json
{
  "specversion": "1.0",
  "type": "com.enterpriseai.document.indexed",
  "source": "/api/v1/documents",
  "id": "uuid",
  "time": "2026-06-15T10:30:00Z",
  "datacontenttype": "application/json",
  "tenantid": "uuid",
  "data": {
    "documentId": "uuid",
    "collectionId": "uuid",
    "chunkCount": 42
  }
}
```

**Reliability**:
- At-least-once delivery (consumer phải idempotent).
- Dead-letter queue (DLQ) cho message fail.
- Retry với exponential backoff.
- Poison message detection.

### 8.1 Multi-Tenancy Manager

**Mục đích**: Quản lý vòng đời tenant, đảm bảo isolation giữa các tenant.

**Data Model**:

```sql
CREATE TABLE tenants (
    id              UUID PRIMARY KEY,
    name            VARCHAR(200) NOT NULL,
    slug            VARCHAR(100) UNIQUE,         -- subdomain
    tier            VARCHAR(20),                 -- "free", "pro", "enterprise"
    status          VARCHAR(20),                 -- "active", "suspended", "deleted"
    settings        JSONB,
    ai_config       JSONB,                       -- TenantAIConfig
    created_at      TIMESTAMPTZ,
    suspended_at    TIMESTAMPTZ,
    deleted_at      TIMESTAMPTZ
);

CREATE TABLE tenant_users (
    tenant_id       UUID REFERENCES tenants(id),
    user_id         UUID,
    role            VARCHAR(50),
    permissions     TEXT[],
    joined_at       TIMESTAMPTZ,
    PRIMARY KEY (tenant_id, user_id)
);
```

**Tenant resolution** (mỗi request):
- Ưu tiên: JWT claim `tenantId`.
- Fallback: subdomain (`acme.platform.com` → tenantId của acme).
- Fallback: header `X-Tenant-Id`.
- Default: reject (nếu không tìm được).

**Isolation strategies** (chọn 1 theo tier):
- **Database per tenant**: Enterprise tier.
- **Schema per tenant**: Pro tier.
- **Row-Level Security**: Free tier (default).

**Tenant lifecycle**:
- Provisioning: tạo DB/schema, seed config, gửi welcome email.
- Suspension: khi hết hạn/violation → block login, giữ data.
- Deletion: soft delete (30 ngày) → hard delete (xóa vĩnh viễn data).
- Data export: theo GDPR/quy định.

### 8.3 Audit & Compliance

**Mục đích**: Ghi lại mọi action quan trọng để phục vụ audit, compliance (SOC2, GDPR, HIPAA).

**Audit log structure**:

```sql
CREATE TABLE audit_logs (
    id              UUID PRIMARY KEY,
    tenant_id       UUID,
    user_id         UUID,
    actor_type      VARCHAR(20),         -- "user", "system", "agent", "api_key"

CREATE INDEX idx_audit_tenant_time ON audit_logs(tenant_id, occurred_at DESC);
CREATE INDEX idx_audit_user ON audit_logs(user_id, occurred_at DESC);
CREATE INDEX idx_audit_resource ON audit_logs(resource_type, resource_id);
```

**What to log** (mặc định):

- Retention: mặc định 1 năm, có thể cấu hình.

**Compliance export**:
- GDPR: data export cho user (right to data portability).
- GDPR: data deletion (right to be forgotten).
- SOC2: báo cáo access pattern, security events.

### 8.4 Secrets & Key Management

```csharp
public interface ISecretsManager

    Task<string> GetSecretAsync(string key, Guid? tenantId = null, CancellationToken ct = default);

    Task RotateAsync(string key, CancellationToken ct = default);
    Task<string> EncryptAsync(string plaintext, CancellationToken ct = default);
    Task<string> DecryptAsync(string ciphertext, CancellationToken ct = default);
}
```

## 10. Phụ lục: Cross-cutting Concerns

### 10.1 Error Handling Strategy

**Error categories**:
1. **User errors** (4xx): invalid input, permission denied → trả về client.
2. **Transient errors** (5xx retryable): network, timeout → auto-retry.
3. **Permanent errors** (5xx non-retryable): bug, configuration → alert + log.
4. **Business errors**: domain rule violation → trả về với message rõ ràng.

**Pattern**:
```csharp
public class Result<T>
{
    public bool IsSuccess { get; }
    public T? Value { get; }
    public Error? Error { get; }
}

public record Error(string Code, string Message, ErrorSeverity Severity, IDictionary<string, object>? Details = null);
```

**Retry policy**:
- Exponential backoff: 1s, 2s, 4s, 8s (cap 30s).
- Jitter: ±20% để tránh thundering herd.
- Max retries: 3 cho LLM call, 5 cho HTTP call, 0 cho user input.

**Circuit breaker** (cho external service):
- Closed: bình thường.
- Open: fail fast khi service down.
- Half-Open: thử lại sau timeout.

### 10.2 Logging Conventions

**Log format** (JSON, một dòng):
```json
{
  "timestamp": "2026-06-15T10:30:00.123Z",
  "level": "Information",
  "message": "Chat completed",
  "traceId": "abc123",
  "spanId": "def456",
  "tenantId": "uuid",
  "userId": "uuid",
  "sessionId": "uuid",
  "properties": {
    "model": "gpt-4o",
    "tokens": 1234,
    "latencyMs": 2345
  }
}
```

**Levels**:
- `Verbose`: chi tiết cực nhỏ (chỉ bật khi debug).
- `Debug`: thông tin debug (chỉ bật ở dev).
- `Information`: sự kiện quan trọng (default production).
- `Warning`: vấn đề không nghiêm trọng.
- `Error`: lỗi cần xem xét.
- `Fatal`: lỗi nghiêm trọng, có thể crash app.

### 10.3 Performance Budget

| Operation | Target (P95) | Hard limit |
|-----------|--------------|------------|
| Simple chat (no RAG) | < 2s | < 5s |
| RAG chat | < 3s | < 8s |
| Vector search | < 200ms | < 500ms |
| Hybrid search | < 400ms | < 1s |
| Document indexing (1MB) | < 10s | < 30s |
| Embedding (1 text) | < 100ms | < 500ms |
| Agent step execution | < 5s | < 30s |
| API request (any) | < 500ms | < 2s |

### 10.4 Security Hardening Checklist

- [ ] Tất cả API endpoint yêu cầu auth (trừ public health).
- [ ] RBAC + ABAC cho mọi resource access.
- [ ] Row-Level Security trong DB cho multi-tenant.
- [ ] Input validation cho mọi request (schema-based).
- [ ] Output encoding chống XSS.
- [ ] SQL parameterization (không string concat).
- [ ] Rate limiting mọi endpoint.
- [ ] HTTPS only, HSTS header.
- [ ] CORS whitelist (không `*`).
- [ ] CSP header cho web UI.
- [ ] Secrets không bao giờ log.
- [ ] PII masked trong log.
- [ ] Encryption at rest cho sensitive data.
- [ ] Audit log immutable (append-only).
- [ ] Dependency scanning (Snyk, Dependabot).
- [ ] Container image scanning (Trivy).
- [ ] Secret rotation tự động.
- [ ] Penetration test hàng năm.

### 10.5 Testing Strategy

**Test pyramid**:
```
        ┌─────────────────┐
        │  E2E Tests      │  (10%)  - Playwright, real flows
        ├─────────────────┤
        │  Integration    │  (30%)  - API + DB + external
        ├─────────────────┤
        │  Unit Tests     │  (60%)  - xUnit, Moq, FluentAssertions
        └─────────────────┘
```

**Specific tests**:
- **Unit**: mỗi module có unit test riêng, coverage > 80%.
- **Integration**: test module kết hợp (RAG + Vector Store + LLM provider mock).
- **Contract test**: đảm bảo provider mới tuân thủ interface (Pact).
- **Performance test**: k6/Gatling đo latency under load.
- **Chaos test**: tắt provider, kill DB → verify failover.
- **Security test**: OWASP ZAP, dependency audit, secret scan.
- **Evaluation test** (cho AI): RAGAS, DeepEval để đo chất lượng RAG/Agent.

**CI pipeline**:
1. Lint + format check.
2. Unit test + coverage gate.
3. Integration test (với Docker compose).
4. Build Docker image.
5. Security scan.
6. Deploy to staging.
7. E2E test on staging.
8. Manual approval → production.

| Concern | Tool | Lý do |
|---------|------|-------|
| Logs | Serilog → Seq (dev) / Loki (prod) | Structured logging |
| Metrics | Prometheus + Grafana | Industry standard |
| Traces | OpenTelemetry → Jaeger | Vendor-neutral |

### 10.7 Deployment Topology (tóm tắt)

**Development**: docker-compose với 1 file cho tất cả service.

**Staging**: Kubernetes (3 node), reduced replicas, separate infra.

**Production**:
- K8s cluster ở cloud (AKS/EKS/GKE).
- Managed DB (Azure Database for PostgreSQL Flexible + pgvector).
- Managed Redis (Azure Cache for Redis).
- Object storage (Azure Blob / S3).
- CDN (CloudFront/Cloudflare) cho static asset.
- WAF (Web Application Firewall) trước gateway.
- Backup hàng ngày, DR site ở region khác.
- Auto-scaling theo CPU + queue depth.
- Blue-green hoặc canary deployment.

### 10.8 Disaster Recovery

- **RPO** (Recovery Point Objective): 1 giờ (backup mỗi giờ).
- **RTO** (Recovery Time Objective): 4 giờ.
- **Backup**: full backup hàng ngày + incremental mỗi giờ, lưu 30 ngày.
- **Cross-region replication**: vector store + DB replicate sang region phụ.
- **Runbook**: tài liệu quy trình restore, failover.
- **Game day**: diễn tập failover 2 lần/năm.
