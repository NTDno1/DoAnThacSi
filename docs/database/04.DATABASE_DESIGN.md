## 1. Tổng quan Chiến lược Database

### 1.1 Kiến trúc Đa Database

Hệ thống sử dụng kiến trúc đa database để tối ưu hóa hiệu suất và đáp ứng các yêu cầu nghiệp vụ khác nhau:

```
┌─────────────────────────────────────────────────────────────────┐
│                      APPLICATION LAYER                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────────────┐  │
│  │  PostgreSQL  │  │    Redis     │  │       MinIO          │  │
│  │     16       │  │   (Cache)    │  │  (Object Storage)    │  │
│  │              │  │              │  │                      │  │
│  │  - Users     │  │  - Session   │  │  - PDF files         │  │
│  │  - Documents │  │  - Cache     │  │  - DOCX files        │  │
│  │  - Chunks    │  │  - Queue     │  │  - Images            │  │
│  │  - Messages  │  │  - Rate Limit│  │  - Other binaries    │  │
│  │  - Vectors   │  │              │  │                      │  │
│  └──────────────┘  └──────────────┘  └──────────────────────┘  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 Vai trò của từng Database

| Database | Vai trò | Dung lượng ước tính | SLA |
|----------|---------|---------------------|-----|
| PostgreSQL 16 | Primary DB, Vector Storage | 50-500 GB | 99.9% |
| Redis | Cache, Session, Queue | 1-10 GB | 99.95% |
| MinIO | Object Storage | 1-10 TB | 99.5% |

### 1.3 Design Principles

1. **Normalized Design**: Giảm thiểu redundancy, đảm bảo data integrity
2. **Vector-native**: Sử dụng pgvector cho vector storage trực tiếp trong PostgreSQL
3. **Scalable**: Hỗ trợ horizontal scaling thông qua partitioning
4. **Audit-friendly**: Tất cả bảng có `created_at`, `updated_at`
5. **Soft Delete**: Các bảng quan trọng hỗ trợ soft delete để phục vụ audit

## 2. Lựa chọn Công nghệ

### 2.1 PostgreSQL 16 với pgvector Extension

#### Tại sao PostgreSQL + pgvector?

**Ưu điểm vượt trội:**

| Tiêu chí | PostgreSQL + pgvector | Pinecone | Milvus | Qdrant |
|----------|----------------------|----------|--------|--------|
| **Tích hợp** | ✅ Native integration | ❌ Separate service | ❌ Separate service | ❌ Separate service |
| **ACID Compliance** | ✅ Full ACID | ❌ Eventual consistency | ⚠️ Partial | ⚠️ Partial |
| **Operational Complexity** | ✅ Single database | ❌ Managed required | ❌ High | ❌ Medium |
| **Cost** | ✅ Low (infra only) | ❌ High (managed) | ⚠️ Medium | ⚠️ Medium |
| **Query Flexibility** | ✅ SQL + Vector | ❌ API only | ⚠️ Limited | ⚠️ Limited |
| **Scale** | 1-10M vectors | Unlimited | Unlimited | Unlimited |

**Kết luận:** Đối với hệ thống quy mô vừa và nhỏ (1-10 triệu vectors), PostgreSQL + pgvector là lựa chọn tối ưu về chi phí và độ phức tạp vận hành.

### 2.2 Redis - Cache và Session

**Use Cases:**
- Session storage cho authentication
- API response caching (search results, document metadata)
- Rate limiting counters
- Job queue (Sidekiq-compatible)

**Redis Data Structures:**

| Key Pattern | Type | TTL | Purpose |
|-------------|------|-----|---------|
| `session:{user_id}` | Hash | 7 days | User session data |
| `cache:doc:{id}` | String (JSON) | 1 hour | Document metadata |
| `cache:search:{hash}` | String (JSON) | 15 min | Search results |
| `ratelimit:{user_id}:{endpoint}` | String | 1 min | Rate limiting |
| `queue:jobs` | List | - | Background job queue |

### 2.3 MinIO - Object Storage

**Use Cases:**
- Lưu trữ file gốc (PDF, DOCX, XLSX)
- Images (avatars, thumbnails)
- Backup files

**Bucket Structure:**

```
documents-bucket/
├── originals/           # File gốc được upload
│   └── {year}/{month}/{day}/{uuid}.{ext}
├── thumbnails/          # Thumbnail cho preview
│   └── {document_id}/thumb_001.jpg
└── processed/           # File đã qua xử lý OCR
    └── {document_id}/
```

## 3. Thiết kế Schema - Các Bảng Chính

### 3.1 Bảng `users` - Người dùng hệ thống

**Mục đích:** Lưu trữ thông tin người dùng trong hệ thống, hỗ trợ phân quyền và authentication.

```sql
-- ================================================================
-- Bảng users: Lưu trữ thông tin người dùng
-- ================================================================
CREATE TABLE users (
    -- Primary key sử dụng UUID thay vì serial để:
    -- 1. Tránh enumeration attacks
    -- 2. Hỗ trợ distributed systems
    -- 3. Merge data từ multiple sources dễ dàng hơn
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- Email là unique identifier cho authentication
    -- Validate bằng application layer để đảm bảo format
    email VARCHAR(255) UNIQUE NOT NULL,
    
    -- Password hash sử dụng bcrypt với cost factor 12
    -- Không bao giờ lưu plain text password
    password_hash VARCHAR(255) NOT NULL,
    
    -- Họ và tên đầy đủ
    full_name VARCHAR(255) NOT NULL,
    
    -- Avatar URL - nullable vì user có thể chưa upload avatar
    -- Sử dụng Gravatar như fallback
    avatar_url VARCHAR(500),
    
    -- Department phục vụ cho việc phân quyền và filtering
    -- Ví dụ: "Kỹ thuật", "Kinh doanh", "Nhân sự"
    department VARCHAR(100),
    
    -- Role xác định quyền hạn trong hệ thống
    -- - admin: Toàn quyền, quản lý users và settings
    -- - manager: Quản lý documents, xem analytics
    -- - user: Upload, search, chat bình thường
    -- - guest: Chỉ xem, không upload hay chat
    role VARCHAR(50) NOT NULL DEFAULT 'user',
    
    -- Check constraint để đảm bảo role hợp lệ
    CONSTRAINT chk_users_role CHECK (
        role IN ('admin', 'manager', 'user', 'guest')
    ),
    
    -- Trạng thái active - soft disable user mà không xóa
    -- User bị disable vẫn giữ lại data và có thể restore
    is_active BOOLEAN DEFAULT TRUE,
    
    -- Timestamps để track lifecycle của record
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    
    -- Track last login để phát hiện tài khoản bất thường
    last_login_at TIMESTAMPTZ,
    
    -- Constraints
    CONSTRAINT chk_users_email_format CHECK (
        email ~* '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$'
    )
);

-- Indexes cho các truy vấn phổ biến
CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_users_role ON users(role);
CREATE INDEX idx_users_department ON users(department);
CREATE INDEX idx_users_active ON users(is_active) WHERE is_active = TRUE;
```

**Design Decisions:**

| Decision | Rationale |
|----------|----------|
| UUID primary key | Bảo mật tốt hơn, hỗ trợ distributed systems |
| TIMESTAMPTZ | Luôn dùng timezone-aware timestamp |
| Soft delete (is_active) | Giữ lại audit trail, có thể restore |
| Separate role field | Linh hoạt hơn enum, dễ thêm role mới |

### 3.2 Bảng `refresh_tokens` - Token làm mới Authentication

**Mục đích:** Lưu trữ refresh tokens để implement long-lived sessions với JWT.

```sql
-- ================================================================
-- Bảng refresh_tokens: Lưu trữ refresh tokens cho JWT authentication
-- ================================================================
CREATE TABLE refresh_tokens (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- Reference đến user sở hữu token
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    
    -- Token value - unique để prevent duplicate tokens
    -- Lưu hashed value để có thể revoke mà không lộ plaintext
    token VARCHAR(500) NOT NULL UNIQUE,
    
    -- Expiration time - refresh token có TTL dài (7-30 days)
    -- Không dùng absolute expiration vì có thể gây race conditions
    expires_at TIMESTAMPTZ NOT NULL,
    
    -- Timestamp tạo token
    created_at TIMESTAMPTZ DEFAULT NOW(),
    
    -- Revocation support - nullable cho đến khi revoke
    revoked_at TIMESTAMPTZ,
    
    -- Ai đã revoke token này (user tự revoke hoặc admin revoke)
    revoked_by UUID REFERENCES users(id),
    
    -- Metadata để track token usage
    user_agent VARCHAR(500),
    ip_address VARCHAR(45)  -- IPv6 compatible
);

-- Indexes
CREATE INDEX idx_refresh_tokens_user ON refresh_tokens(user_id);
CREATE INDEX idx_refresh_tokens_token ON idx_refresh_tokens_token;
CREATE INDEX idx_refresh_tokens_expires ON refresh_tokens(expires_at);

-- Partial index cho active tokens (performance optimization)
CREATE INDEX idx_refresh_tokens_active ON refresh_tokens(user_id) 
WHERE revoked_at IS NULL AND expires_at > NOW();
```

**Security Notes:**
- Refresh tokens nên được hashed trước khi lưu vào database
- TTL ngắn (7-30 days) giới hạn damage nếu token bị leak
- Cascade delete khi user bị xóa để tránh orphaned tokens

```sql
-- ================================================================
```

### 3.4 Bảng `documents` - Tài liệu chính

**Mục đích:** Lưu trữ metadata của documents và trạng thái indexing.

```sql
-- ================================================================
-- Bảng documents: Metadata của tài liệu
-- ================================================================
CREATE TABLE documents (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- Tiêu đề document - do user nhập hoặc extracted từ filename
    title VARCHAR(500) NOT NULL,
    
    -- Tên file gốc khi upload
    original_filename VARCHAR(500) NOT NULL,
    
    -- Đường dẫn trong MinIO object storage
    -- Format: {bucket}/{path}/{filename}
    storage_path VARCHAR(1000) NOT NULL,
    
    -- Kích thước file (bytes) - để display và quota management
    file_size BIGINT NOT NULL,
    
    -- MIME type để xác định cách xử lý
    -- Ví dụ: application/pdf, application/vnd.openxmlformats-officedocument.wordprocessingml.document
    mime_type VARCHAR(100) NOT NULL,
    
    -- SHA-256 hash để deduplication
    -- Nếu 2 files có cùng hash, chỉ lưu 1 bản
    file_hash VARCHAR(64) NOT NULL,
    
    -- Foreign key đến category
    -- Nullable vì document có thể chưa được phân loại
    category_id UUID REFERENCES document_categories(id) ON DELETE SET NULL,
    
    -- Ai đã upload document này
    uploader_id UUID NOT NULL REFERENCES users(id),
    
    -- Trạng thái indexing để track tiến trình
    -- - pending: Chờ xử lý
    -- - processing: Đang extract text và generate embeddings
    -- - indexed: Đã hoàn thành, có thể search
    -- - failed: Xử lý thất bại, cần retry hoặc manual intervention
    -- - deleted: Đã xóa (soft delete)
    status VARCHAR(50) DEFAULT 'pending',
    CONSTRAINT chk_documents_status CHECK (
        status IN ('pending', 'processing', 'indexed', 'failed', 'deleted')
    ),
    
    -- Text đã extract từ document (sau OCR nếu cần)
    -- Có thể là NULL nếu extraction thất bại
    extracted_text TEXT,
    
    -- Số trang - hữu ích cho pagination và display
    page_count INT,
    
    -- Ngôn ngữ chính của document (để chọn embedding model phù hợp)
    -- ISO 639-1 codes: 'vi', 'en', 'zh', 'ja', 'ko', etc.
    language VARCHAR(10) DEFAULT 'vi',
    
    -- Metadata bổ sung dưới dạng JSONB
    -- Ví dụ: {"author": "Nguyen Van A", "created_date": "2024-01-15", "tags": ["HR", "policy"]}
    metadata JSONB DEFAULT '{}',
    
    -- Timestamps
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    
    -- Khi nào document được indexed thành công
    indexed_at TIMESTAMPTZ,
    
    -- Soft delete flag
    is_deleted BOOLEAN DEFAULT FALSE,
    
    -- Error message nếu indexing failed
    error_message TEXT,
    
    -- Retry count để track số lần retry
    retry_count INT DEFAULT 0,
    
    -- Content hash để detect changes (khác với file_hash)
    content_hash VARCHAR(64),
    
    -- Constraints
    CONSTRAINT chk_documents_file_size CHECK (file_size > 0),
    CONSTRAINT chk_documents_page_count CHECK (page_count > 0)
);

-- Indexes cho các truy vấn phổ biến
CREATE INDEX idx_documents_category ON documents(category_id) WHERE is_deleted = FALSE;
CREATE INDEX idx_documents_uploader ON documents(uploader_id) WHERE is_deleted = FALSE;
CREATE INDEX idx_documents_status ON documents(status) WHERE status != 'deleted';
CREATE INDEX idx_documents_created ON documents(created_at DESC);
CREATE INDEX idx_documents_hash ON documents(file_hash);

-- Composite index cho common query pattern
CREATE INDEX idx_documents_category_status ON documents(category_id, status) 
WHERE is_deleted = FALSE;

-- Full-text search index
CREATE INDEX idx_documents_fts ON documents 
USING gin (to_tsvector('vietnamese', title || ' ' || COALESCE(extracted_text, '')));

-- GIN index trên metadata JSONB để search theo tags, author, etc.
CREATE INDEX idx_documents_metadata ON documents USING gin (metadata);
```

**Design Decisions:**

| Decision | Rationale |
|----------|----------|
| Separate `extracted_text` field | Cho phép re-indexing mà không cần re-upload file |
| `file_hash` for deduplication | Tiết kiệm storage, tránh duplicate files |
| `metadata` as JSONB | Linh hoạt, schema-less, queryable với GIN index |
| `status` field | Cho phép track indexing progress, retry failed items |

### 3.5 Bảng `document_chunks` - Vector Embeddings (CRITICAL)

**Mục đích:** Lưu trữ text chunks và vector embeddings cho semantic search. Đây là bảng quan trọng nhất cho RAG functionality.

```sql
-- ================================================================
-- Bảng document_chunks: Lưu trữ text chunks và vector embeddings
-- CRITICAL: Bảng này chứa dữ liệu vector cho semantic search
-- ================================================================
CREATE TABLE document_chunks (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- Reference đến document cha
    document_id UUID NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    
    -- Thứ tự chunk trong document (0-indexed)
    -- Unique với document_id để đảm bảo không duplicate chunks
    chunk_index INT NOT NULL,
    
    -- Text content của chunk
    -- Đây là text sẽ được embed và cũng là text sẽ được trả về trong search results
    content TEXT NOT NULL,
    
    -- Hash của content để deduplication
    -- Nếu 2 chunks có cùng hash, chỉ giữ lại 1
    content_hash VARCHAR(64) NOT NULL,
    
    -- Vector embedding (pgvector column)
    -- Số chiều phụ thuộc vào embedding model:
    -- - text-embedding-3-small: 1536 dimensions
    -- - text-embedding-3-large: 3072 dimensions
    -- Sử dụng 1536 dimensions (tối ưu cost/quality)
    embedding vector(1536),
    
    -- Số trang trong document gốc mà chunk này thuộc về
    -- Hữu ích để highlight và citation
    page_number INT,
    
    -- Tiêu đề section/chapter mà chunk thuộc về
    -- Ví dụ: "Chapter 3: Employee Benefits", "Section 2.1: Leave Policy"
    section_title VARCHAR(500),
    
    -- Vị trí ký tự bắt đầu và kết thúc trong document gốc
    -- Dùng để reconstruct context và tránh overlap
    start_char_position INT,
    end_char_position INT,
    
    -- Token count (ước tính) - hữu ích cho:
    -- 1. Đảm bảo không vượt quá context window của LLM
    -- 2. Tính toán chi phí API
    token_count INT,
    
    -- Metadata bổ sung
    -- Ví dụ: {"headings": ["HR Policy", "Leave"], "importance": 0.8}
    metadata JSONB DEFAULT '{}',
    
    -- Timestamp tạo chunk
    created_at TIMESTAMPTZ DEFAULT NOW(),
    
    -- Unique constraint
    CONSTRAINT uq_chunks_document_index UNIQUE (document_id, chunk_index)
);

-- ================================================================
-- VECTOR INDEX - Critical cho semantic search performance
-- ================================================================

-- HNSW Index (Hierarchical Navigable Small World)
-- Đây là index quan trọng nhất cho vector similarity search
-- 
-- Parameters:
-- - m: Số connections mỗi node (default 16)
--   - Giá trị cao hơn = chất lượng index tốt hơn, nhưng tốn memory
--   - Khuyến nghị: 16-64
-- - ef_construction: Kích thước của dynamic candidate list
--   - Giá trị cao hơn = chất lượng index tốt hơn, nhưng build chậm hơn
--   - Khuyến nghị: 200-400
--
-- Trade-offs:
-- - High m (32-64) + High ef (200-400): Chất lượng cao, build/ram chậm
-- - Low m (8-16) + Low ef (64-128): Build nhanh, RAM thấp, chất lượng thấp hơn

CREATE INDEX idx_chunks_embedding_hnsw ON document_chunks 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 200);

-- Alternative: IVFFlat Index cho very large datasets (> 5M vectors)
-- IVFFlat build nhanh hơn nhưng query chậm hơn HNSW
-- 
-- CREATE INDEX idx_chunks_embedding_ivfflat ON document_chunks 
-- USING ivfflat (embedding vector_cosine_ops) 
-- WITH (lists = 100);

-- ================================================================
-- ADDITIONAL INDEXES
-- ================================================================

-- Index để tìm chunks theo document (cho context retrieval)
CREATE INDEX idx_chunks_document ON document_chunks(document_id);

-- Index để deduplicate chunks
CREATE INDEX idx_chunks_hash ON document_chunks(content_hash);

-- Composite index cho queries cần cả document và chunk order
CREATE INDEX idx_chunks_doc_index ON document_chunks(document_id, chunk_index);
```

**Chunking Strategy Details:**

```sql
-- Ví dụ chunking configuration
-- Chunk size: 512 tokens (~2000 characters)
-- Chunk overlap: 50 tokens (~200 characters)
-- Min chunk size: 100 tokens
-- Max chunk size: 1024 tokens

-- Khi embedding:
-- 1. Split document thành chunks với overlap
-- 2. Generate embedding cho mỗi chunk
-- 3. Store chunk với metadata (page_number, section_title, etc.)

-- Khi search:
-- 1. Embed query
-- 2. Tìm top-k chunks gần nhất bằng vector similarity
-- 3. Expand context bằng cách include adjacent chunks nếu cần
-- 4. Return chunks với citations
```

### 3.6 Bảng `chat_sessions` - Phiên hỏi đáp

**Mục đích:** Lưu trữ chat sessions để maintain conversation history.

```sql
-- ================================================================
-- Bảng chat_sessions: Phiên hỏi đáp (RAG conversations)
-- ================================================================
CREATE TABLE chat_sessions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- User sở hữu session
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    
    -- Tiêu đề session - có thể auto-generated hoặc user-defined
    -- Ví dụ: "Hỏi về chính sách nghỉ phép", "Tìm hiểu quy trình onboarding"
    title VARCHAR(255),
    
    -- Timestamps
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    
    -- Số lượng messages trong session (cache count)
    message_count INT DEFAULT 0,
    
    -- Preview của message cuối cùng (cho display in list)
    last_message_preview TEXT,
    
    -- Model được sử dụng trong session
    -- Có thể thay đổi giữa các messages (user preference)
    model VARCHAR(50) DEFAULT 'gpt-4o-mini',
    
    -- Session status
```

## 5. Chiến lược pgvector

### 5.1 Tại sao pgvector?

**pgvector là lựa chọn tối ưu cho hệ thống này vì:**

1. **Tích hợp Native**: Không cần separate vector database
2. **ACID Compliance**: Đảm bảo consistency giữa metadata và vectors
3. **Single Source of Truth**: Một database cho cả relational và vector data
4. **Operational Simplicity**: Giảm độ phức tạp vận hành
5. **Cost Effective**: Chỉ tốn chi phí infra cho PostgreSQL
6. **Sufficient Scale**: Đủ cho 1-10 triệu vectors với performance tốt

### 5.2 Embedding Model Selection

| Model | Dimensions | Performance | Cost | Recommended |
|-------|-----------|-------------|------|-------------|
| **text-embedding-3-small** | 1536 | ⚡⚡⚡⚡⚡ | $ | ✅ **Recommended** |
| text-embedding-3-large | 3072 | ⚡⚡⚡⚡⚡ | $$$ | Cho accuracy cao |
| text-embedding-ada-002 | 1536 | ⚡⚡⚡ | $$ | Legacy option |

**Khuyến nghị:** `text-embedding-3-small` với 1536 dimensions

**Rationale:**
- Cost thấp nhất ($0.02/1K tokens vs $0.195/1K tokens cho ada-002)
- Performance tốt cho most use cases
- 1536 dimensions không quá lớn cho pgvector indexing

### 5.3 Distance Metrics

pgvector hỗ trợ 3 distance metrics:

```sql
-- 1. Cosine Distance (<=>) - RECOMMENDED
-- Đo góc giữa 2 vectors, không quan tâm magnitude
-- Best cho: semantic search, text embeddings
SELECT embedding <=> $query_embedding FROM document_chunks;

-- 2. Euclidean Distance (<->)
-- Khoảng cách Euclidean trong vector space
-- Best cho: recommendation systems, image similarity
SELECT embedding <-> $query_embedding FROM document_chunks;

-- 3. Negative Inner Product (<#>)
-- Inner product (higher is more similar)
-- Best cho: maximizing dot product (e.g., collaborative filtering)
SELECT embedding <#> $query_embedding FROM document_chunks;
```

**Chọn Cosine Similarity vì:**
- Không bị ảnh hưởng bởi document length
- Phù hợp với semantic meaning của text
- Industry standard cho text embeddings

### 5.4 Index Types Comparison

| Index Type | Build Time | Query Speed | Memory | Accuracy | Best For |
|------------|------------|-------------|--------|----------|----------|
| **HNSW** | Slow (phút-giờ) | ⚡⚡⚡⚡⚡ | High | ~95% | Production < 1M |
| IVFFlat | Fast (giây-phút) | ⚡⚡⚡ | Low | ~90-95% | > 1M vectors |
| None (Brute Force) | N/A | ⚡ | Low | 100% | < 10k vectors |

**HNSW Configuration:**

```sql
-- HNSW Index với recommended parameters
CREATE INDEX idx_chunks_embedding_hnsw ON document_chunks 
USING hnsw (embedding vector_cosine_ops)
WITH (
    m = 16,                    -- Connections per node (8-64 recommended)
    ef_construction = 200      -- Build quality (64-400 recommended)
);

-- Index size estimation:
-- ~ 1536 dimensions × 4 bytes (float32) × 1.5 (HNSW overhead) = ~9KB per vector
-- 1M vectors ≈ 9GB index
```

### 5.5 Vector Query Examples

#### 5.5.1 Basic Semantic Search

```sql
-- Tìm top 10 chunks gần nhất với query
SELECT 
    dc.id,
    dc.document_id,
    d.title AS document_title,
    dc.content,
    dc.page_number,
    dc.section_title,
    1 - (dc.embedding <=> $1::vector) AS similarity_score
FROM document_chunks dc
JOIN documents d ON dc.document_id = d.id
WHERE d.is_deleted = FALSE
ORDER BY dc.embedding <=> $1::vector
LIMIT 10;
```

#### 5.5.2 Hybrid Search (Semantic + Keyword)

```sql
-- Kết hợp vector similarity với PostgreSQL full-text search
-- Alpha = 0.7: 70% weight cho semantic, 30% cho keyword
WITH semantic_results AS (
    SELECT 
        dc.id,
        dc.document_id,
        dc.content,
        1 - (dc.embedding <=> $1::vector) AS semantic_score
    FROM document_chunks dc
    JOIN documents d ON dc.document_id = d.id
    WHERE d.is_deleted = FALSE
),
keyword_results AS (
    SELECT 
        dc.id,
        dc.document_id,
        ts_rank(
            to_tsvector('vietnamese', dc.content),
            plainto_tsquery('vietnamese', $2)
        ) AS keyword_score
    FROM document_chunks dc
    JOIN documents d ON dc.document_id = d.id
    WHERE d.is_deleted = FALSE
),
combined AS (
    SELECT 
        sr.id,
        sr.document_id,
        sr.content,
        sr.semantic_score,
        COALESCE(kr.keyword_score, 0) AS keyword_score,
        (0.7 * sr.semantic_score) + (0.3 * COALESCE(kr.keyword_score, 0)) AS combined_score
    FROM semantic_results sr
    LEFT JOIN keyword_results kr ON sr.id = kr.id
)
SELECT 
    id,
    document_id,
    content,
    semantic_score,
    keyword_score,
    combined_score
FROM combined
ORDER BY combined_score DESC
LIMIT 10;
```

#### 5.5.3 RAG Context Retrieval

```sql
-- Lấy context cho RAG với metadata và citations
WITH relevant_chunks AS (
    SELECT 
        dc.id AS chunk_id,
        dc.document_id,
        d.title AS document_title,
        dc.content,
        dc.page_number,
        dc.section_title,
        dc.token_count,
        1 - (dc.embedding <=> $1::vector) AS relevance_score,
        ROW_NUMBER() OVER (ORDER BY dc.embedding <=> $1::vector) AS rank
    FROM document_chunks dc
    JOIN documents d ON dc.document_id = d.id
    WHERE d.is_deleted = FALSE
    ORDER BY dc.embedding <=> $1::vector
    LIMIT 5
)
SELECT 
    chunk_id,
    document_id,
    document_title,
    content,
    page_number,
    section_title,
    token_count,
    relevance_score,
    rank,
    -- Build citation format
    jsonb_build_object(
        'document_id', document_id,
        'chunk_id', chunk_id,
        'title', document_title,
        'page', page_number,
        'excerpt', LEFT(content, 200) || '...'
    ) AS citation
FROM relevant_chunks;
```

#### 5.5.4 MMR (Maximum Marginal Relevance) for Diversity

```sql
-- MMR: Cân bằng relevance và diversity trong retrieval
-- Giúp tránh trả về nhiều chunks từ cùng document
WITH query_embedding AS (
    SELECT $1::vector AS embedding
),
chunks_with_scores AS (
    SELECT 
        dc.id,
        dc.document_id,
        dc.content,
        1 - (dc.embedding <=> (SELECT embedding FROM query_embedding)) AS relevance
    FROM document_chunks dc
    JOIN documents d ON dc.document_id = d.id
    WHERE d.is_deleted = FALSE
),
mmr_selection AS (
    SELECT 
        cws.id,
        cws.document_id,
        cws.content,
        cws.relevance,
        COALESCE(
            MAX(cws2.relevance) FILTER (
                WHERE cws.document_id = cws2.document_id AND cws.id != cws2.id
            ),
            0
        ) AS doc_diversity_score
    FROM chunks_with_scores cws
    LEFT JOIN chunks_with_scores cws2 ON cws2.id IN (
        SELECT id FROM chunks_with_scores ORDER BY relevance DESC LIMIT 10
    )
    GROUP BY cws.id, cws.document_id, cws.content, cws.relevance
)
SELECT 
    id,
    document_id,
    content,
    relevance,
    (0.7 * relevance) - (0.3 * doc_diversity_score) AS mmr_score
FROM mmr_selection
ORDER BY mmr_score DESC
LIMIT 10;
```

```sql
-- Tạo audit log table
CREATE TABLE audit_logs (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    table_name VARCHAR(100) NOT NULL,
    action VARCHAR(20) NOT NULL,
    row_id UUID NOT NULL,
    old_data JSONB,
    new_data JSONB,
    user_id UUID,
    ip_address VARCHAR(45),
    timestamp TIMESTAMPTZ DEFAULT NOW()
);

-- Trigger function cho audit
CREATE OR REPLACE FUNCTION audit_trigger()
RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO audit_logs (table_name, action, row_id, new_data, user_id)
        VALUES (TG_TABLE_NAME, TG_OP, NEW.id, to_jsonb(NEW), current_setting('app.user_id', TRUE));
        RETURN NEW;
    ELSIF TG_OP = 'UPDATE' THEN
        INSERT INTO audit_logs (table_name, action, row_id, old_data, new_data, user_id)
        VALUES (TG_TABLE_NAME, TG_OP, OLD.id, to_jsonb(OLD), to_jsonb(NEW), current_setting('app.user_id', TRUE));
        RETURN NEW;
    ELSIF TG_OP = 'DELETE' THEN
        INSERT INTO audit_logs (table_name, action, row_id, old_data, user_id)
        VALUES (TG_TABLE_NAME, TG_OP, OLD.id, to_jsonb(OLD), current_setting('app.user_id', TRUE));
        RETURN OLD;
    END IF;
END;
$$ LANGUAGE plpgsql;

-- Attach trigger to sensitive tables
CREATE TRIGGER audit_documents
    AFTER INSERT OR UPDATE OR DELETE ON documents
    FOR EACH ROW EXECUTE FUNCTION audit_trigger();
```

### 13.2 Glossary

| Term | Definition |
|------|------------|
| **Vector Embedding** | Numerical representation của text/image/audio trong vector space |
| **Semantic Search** | Search dựa trên meaning thay vì exact keyword matching |
| **RAG** | Retrieval-Augmented Generation - kỹ thuật enhance LLM với external knowledge |
| **Chunking** | Process chia document thành smaller pieces để embed |
| **HNSW** | Hierarchical Navigable Small World - algorithm cho approximate nearest neighbor search |
| **Cosine Similarity** | Measure của similarity giữa 2 vectors dựa trên angle |
| **Hybrid Search** | Kết hợp semantic search với keyword search |
| **MMR** | Maximum Marginal Relevance - technique để diversify search results |
| **PITR** | Point-in-Time Recovery - ability để restore DB tại any point in time |
