## 1. Triết lý lập kế hoạch

### 1.1 Bài toán đặt ra

Enterprise AI Platform có **~40 module**, **7 layer**, code ước tính **200.000 - 500.000 dòng** (kèm test). Một lần prompt AI không thể bao quát hết → phải chia phase.

### 1.2 Giới hạn thực tế của AI

| Giới hạn | Giá trị | Ý nghĩa |
|----------|---------|---------|
| Context window tối đa | 200.000 token | Tổng input + output |
| Token trung bình / dòng code C# | ~50-80 token | Bao gồm comment |
| Code C# tối đa / lần prompt | ~2.500 - 4.000 dòng | Nếu chỉ code, không kèm test |
| Code C# tối đa / lần prompt (kèm test + doc) | ~1.500 - 2.500 dòng | Thực tế với 1 module phức tạp |
| Số file C# tối đa / lần prompt | 10-15 file | Phụ thuộc kích thước trung bình |

### 1.3 Chiến lược chia Phase

**Modular Monolith trước, Microservice sau** (đã chốt trong kiến trúc tổng thể).

Mỗi Phase:
- Có **runtime chạy được** (end-to-end working software).
- Có **deliverable demo được** cho stakeholder.
- Có **test pass được** (unit + integration).
- Có **document đầy đủ** cho AI ở phase sau đọc.

## 2. Nguyên tắc chia Phase (cho AI Gen Code)

### 2.1 Nguyên tắc "Vertical Slice"

Mỗi phase cắt **theo chiều dọc** (full stack cho 1 tính năng), KHÔNG cắt ngang (làm hết 1 layer rồi mới sang layer khác).

**Ví dụ đúng** (Phase 1):
- Làm 1 luồng chat đơn giản: Frontend input → API Gateway → LLM Provider (Ollama) → trả response về Frontend → hiển thị.
- Phase này chạm: Frontend, Gateway, Provider Abstraction, Model Registry, Configuration, Multi-tenancy (đơn giản).

**Ví dụ sai**:
- Làm hết tất cả AI Provider trước (Ollama, OpenAI, Anthropic...) → quá nhiều file, vượt token.
- Làm hết Frontend skeleton trước → không có Backend để integrate.

### 2.2 Nguyên tắc "Walking Skeleton"

Phase 1 = Walking Skeleton: hệ thống nhỏ nhất có thể chạy end-to-end. Các phase sau **làm dày thêm** chức năng.

```
Phase 1: Chat với Ollama local (1 model, 1 user, 1 tenant)
Phase 2: Thêm tool calling, multi-LLM provider
Phase 3: Thêm RAG, document upload
Phase 4: Thêm Agent, planning, HITL
Phase 5: Thêm multi-tenant đầy đủ, audit, security
```

### 2.3 Nguyên tắc "Stable Interface"

Mỗi phase phải **cam kết interface** ở cuối phase. Phase sau dùng interface đó, không được sửa.

Nếu cần sửa interface → phải có ADR (Architecture Decision Record) + migration plan.

### 2.4 Nguyên tắc "200k Token Budget"

Mỗi phase khi viết prompt phải có file phase chứa:
- **Phần A - Context ngắn gọn** (khoảng 5.000 - 8.000 token): tóm tắt phase, mục tiêu, kiến trúc tổng quan.
- **Phần B - Spec chi tiết** (khoảng 15.000 - 25.000 token): interface, data model, luồng, acceptance criteria.
- **Phần C - Coding convention + Tech stack** (khoảng 3.000 - 5.000 token): để AI gen code đúng style.
- **Phần D - Output mong muốn** (khoảng 2.000 - 3.000 token): danh sách file, cấu trúc thư mục.

**Tổng file phase**: ~30.000 - 40.000 token. Khi prompt cho AI, ghép thêm:
- File kiến trúc liên quan (Module Detail) ~5.000-10.000 token.
- File phase trước (nếu cần tham chiếu) ~5.000-10.000 token.
- Các file code đã có (nếu cần refactor) ~10.000-30.000 token.

**Tổng context khi prompt**: ~50.000 - 90.000 token, còn dư ~110.000 - 150.000 token cho AI gen code output.

### 2.5 Nguyên tắc "Checkpoint & Tag"

Mỗi phase kết thúc phải:
- **Git tag**: `v0.1.0-phase1`, `v0.2.0-phase2`...
- **Demo chạy được** (kèm video/screenshot).
- **Test coverage** ≥ 60% cho business logic, 100% cho critical path.
- **CHANGELOG** cập nhật.
- **README phase** mô tả cách chạy, test, demo.

## 5. Quy ước chung cho mọi Phase

### 5.1 Coding Convention

- **Ngôn ngữ code**: Tiếng Anh (identifier, comment, log message).
- **Ngôn ngữ tài liệu**: Tiếng Việt (docs, README, CHANGELOG, ADR).
- **Naming**: PascalCase cho class/method/property, camelCase cho biến local, UPPER_SNAKE cho const.
- **File header**: mỗi file có 1 dòng comment mô tả ngắn gọn mục đích.
- **Public API**: phải có XML doc comment (`///`).
- **Async**: mọi method I/O-bound phải async, suffix `Async`, nhận `CancellationToken`.
- **Error handling**: dùng `Result<T>` pattern hoặc throw `DomainException` - KHÔNG silent swallow exception.
- **Logging**: dùng `ILogger<T>`, structured logging với Serilog, KHÔNG log PII, KHÔNG log secret.
- **Dependency Injection**: constructor injection, interface trước.
- **Immutability**: prefer record (immutable) cho DTO/Event.
- **Test**: mỗi public class phải có unit test tương ứng, test naming `MethodName_StateUnderTest_ExpectedBehavior`.

### 5.2 Quy ước Commit & Branch

- **Branch strategy**: GitFlow đơn giản hóa
  - `main` - branch chính, luôn chạy được.
  - `develop` - branch tích hợp.
  - `feature/phaseX-moduleY` - branch cho từng module.
  - `hotfix/*` - fix khẩn cấp.
- **Commit message**: Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:`).
- **Mỗi phase** = 1 release branch, merge vào `main` qua PR.
- **PR review**: bắt buộc 1 approver, tự review qua checklist.

### 5.3 Definition of Done cho mỗi Phase

Một phase được coi là **hoàn thành** khi:

1. ✅ **Code complete**: tất cả file trong scope đã được viết và committed.
2. ✅ **Build pass**: `dotnet build` exit code 0, không có warning (trừ warning acknowledged).
3. ✅ **Test pass**: `dotnet test` exit code 0, coverage ≥ 60% cho business logic.
4. ✅ **Lint pass**: không có lỗi từ analyzer (StyleCop, Roslynator).
5. ✅ **Manual test**: demo flow chạy được end-to-end, có video/screenshot.
6. ✅ **Documentation**: README phase, ADR (nếu có quyết định kiến trúc mới), CHANGELOG cập nhật.
7. ✅ **Container build**: `docker compose up` chạy được, app accessible.
8. ✅ **Git tag**: tag version được push.
9. ✅ **Backward compatibility**: phase mới không phá vỡ phase trước.
10. ✅ **Interface committed**: mọi public interface được document và stable.

### 5.4 Quy ước Naming cho File Phase

Tên file phase được đánh số thứ tự để dễ tham chiếu:
- `01.MASTER_PLAN.md` (file này)
- `02.PHASE_01_FOUNDATION.md`

- `04.PHASE_03_AGENT_INTEGRATION.md`

## 6. Quy trình làm việc với AI

### 6.1 Quy trình prompt AI tổng quát

```
Bước 1: Đọc file phase tương ứng (file phase nào đang triển khai).
         ↓
Bước 2: Đọc file kiến trúc liên quan (02.MODULE_DETAILED_ARCHITECTURE.md).
         ↓
Bước 3: Prompt AI với input:
         - File phase
         - Phần kiến trúc liên quan
         - Code base hiện tại (nếu refactor)
         ↓
Bước 4: AI gen code theo cấu trúc thư mục đã định.
         ↓
Bước 5: Build, test, fix bug (có thể dùng AI để fix).
         ↓
Bước 6: Commit theo convention.
         ↓
Bước 7: Update CHANGELOG, README, demo.
         ↓
Bước 8: Merge vào main, tag version.
```

### 6.2 Template Prompt cho AI

```markdown
## Context

Bạn đang code cho dự án Enterprise AI Platform (.NET 8, ASP.NET Core).
Stack: [liệt kê từ file phase]
Phase hiện tại: Phase X - [tên phase]
Module cần code: [tên module]

## Tài liệu tham chiếu

### File 1: Phase X specification
[Nội dung file phase X]

### File 2: Module detailed architecture
[Phần liên quan trong file 02.MODULE_DETAILED_ARCHITECTURE.md]

### File 3: Tech stack & convention
[Đoạn 5.1 và 5.2 từ file này]

### File 4: Existing code (nếu có)
[Code base hiện tại cần tham chiếu]

## Yêu cầu

1. Gen code đầy đủ cho module [tên module] theo spec.
2. Tuân thủ coding convention tại Mục 5.1.
3. Tạo file theo đúng cấu trúc thư mục tại Mục [X trong file phase].
4. Viết unit test cho mỗi public class.
5. Tạo migration EF Core nếu có thay đổi schema.
6. Comment bằng Tiếng Anh cho code, Tiếng Việt cho README/doc.

## Output mong muốn

- Danh sách file cần tạo
- Code đầy đủ của từng file
- Test cho từng file
- Migration (nếu có)
- Hướng dẫn verify

## Giới hạn

- KHÔNG gen code ngoài scope của phase này.
- KHÔNG sửa interface đã chốt ở phase trước.
- Tổng output KHÔNG quá ~150.000 token (để trừ hao).
```

### 6.3 Quy trình review code do AI gen

Sau khi AI gen code, **luôn phải** review theo checklist:

- [ ] Code build được (`dotnet build`).
- [ ] Test pass (`dotnet test`).
- [ ] Code tuân thủ coding convention.
- [ ] Không có secret/API key hardcoded.
- [ ] Không có PII trong log.
- [ ] Async/await đúng cách, có CancellationToken.
- [ ] Dependency injection đúng.
- [ ] Migration an toàn (không drop data).
- [ ] Interface public có XML doc.
- [ ] Test coverage đạt yêu cầu.
- [ ] README/doc đầy đủ.

### 6.4 Khi AI gen code sai / thiếu

**Không nên**:
- Prompt lại toàn bộ phase (tốn token, mất context).
- Bỏ qua lỗi.

**Nên**:
- Đọc kỹ output, xác định phần sai.
- Prompt lại với diff cụ thể: "Trong file X, function Y đang làm Z, cần sửa thành W vì lý do L".
- Tận dụng follow-up prompt để fix incremental.

### 6.5 Quản lý Token khi Prompt

| Loại file | Kích thước tối đa khuyến nghị |
|-----------|-------------------------------|
| File phase | ~30.000 - 40.000 token |
| File kiến trúc (trích đoạn) | ~5.000 - 10.000 token |
| Code base (trích đoạn tham chiếu) | ~10.000 - 30.000 token |
| Prompt template + yêu cầu | ~3.000 - 5.000 token |
| **Tổng input** | **~50.000 - 80.000 token** |
| Output AI gen code | ~80.000 - 120.000 token |
| **Tổng sử dụng** | **~130.000 - 200.000 token** |

**Khi vượt giới hạn**:
- Chia nhỏ module thành sub-module.
- Prompt theo từng nhóm file (VD: prompt cho "interface + DTO", sau đó prompt cho "implementation", sau đó prompt cho "test").
- Dùng follow-up prompt để build từng phần.
