## 2. Kiến trúc Clean Architecture

### 2.1 Tổng quan Nguyên tắc Clean Architecture

Clean Architecture (theo Robert C. Martin) là nguyên tắc thiết kế phần mềm giúp tách biệt rõ ràng các mối quan tâm (separation of concerns) thông qua các lớp (layers) độc lập. Trong hệ thống này, chúng ta áp dụng Clean Architecture kết hợp với **Layered Architecture** truyền thống của .NET để đạt được:

- **Khả năng kiểm thử cao** (High Testability): Các lớp inner không phụ thuộc vào outer layers
- **Khả năng bảo trì** (Maintainability): Code được tổ chức rõ ràng theo chức năng
- **Khả năng mở rộng** (Extensibility): Dễ dàng thêm tính năng mới
- **Tính độc lập** (Independence): Có thể thay đổi database, UI mà không ảnh hưởng core business

## 3. Kiến trúc CQRS

### 3.1 Tổng quan CQRS Pattern

**CQRS (Command Query Responsibility Segregation)** là pattern phân tách rõ ràng giữa read (queries) và write (commands) operations. Trong hệ thống RAG, đây là pattern lý tưởng vì:

- **Tỷ lệ Read/Write**: Semantic search là read-heavy (90% reads, 10% writes)
- **Optimize riêng biệt**: Read model có thể denormalize, write model normalized
- **Scaling độc lập**: Scale read replicas riêng biệt với write primary
- **Caching hiệu quả**: Query side dễ cache với deterministic keys

// Example: CQRS Pattern Implementation

// ========== COMMANDS ==========

// Document Commands
public record CreateDocumentCommand(

) : IRequest<Result<DocumentDto>>;

    string Title,
    string? Description
) : IRequest<Result<DocumentDto>>;

// Chat Commands
public record SendChatMessageCommand(
    Guid? ChatId,
    string Message,
    Guid? CollectionId,
    bool Stream = true
) : IRequest<IAsyncEnumerable<ChatStreamResponse>>;

// ========== QUERIES ==========

// Document Queries
public record GetDocumentByIdQuery(Guid DocumentId) 
    : IRequest<Result<DocumentDetailDto>>;

public record GetDocumentListQuery(
    int Page = 1,
    int PageSize = 20,
    Guid? CollectionId = null,
    string? SearchTerm = null,
    DocumentStatus? Status = null
) : IRequest<PagedResult<DocumentListDto>>;

// Search Queries
public record SearchDocumentsQuery(
    string QueryText,
    Guid? CollectionId = null,
    int TopK = 10,
    float MinSimilarity = 0.7f,
    bool IncludeMetadata = true
) : IRequest<Result<SearchResultDto>>;

// Chat Queries
public record GetChatHistoryQuery(
    Guid ChatId,
    int Page = 1,
    int PageSize = 50
) : IRequest<Result<ChatHistoryDto>>;

// ========== HANDLERS ==========

public class SearchDocumentsHandler : IRequestHandler<SearchDocumentsQuery, Result<SearchResultDto>>
{
    private readonly IChunkRepository _chunkRepository;
    private readonly IEmbeddingService _embeddingService;
    private readonly ICacheService _cacheService;
    private readonly ILogger<SearchDocumentsHandler> _logger;

    public async Task<Result<SearchResultDto>> Handle(
        SearchDocumentsQuery request, 
        CancellationToken cancellationToken)
    {
        // 1. Check cache
        var cacheKey = $"search:{ComputeHash(request)}";
        var cached = await _cacheService.GetAsync<SearchResultDto>(cacheKey);
        if (cached != null)
        {
            cached.FromCache = true;
            return Result<SearchResultDto>.Success(cached);
        }

        // 2. Generate embedding
        var stopwatch = Stopwatch.StartNew();
        var queryEmbedding = await _embeddingService.GenerateEmbeddingAsync(request.QueryText);

        // 3. Vector search
        var results = await _chunkRepository.SearchAsync(
            queryEmbedding,
            new SearchFilters 
            { 
                CollectionId = request.CollectionId,
                MinSimilarity = request.MinSimilarity
            },
            request.TopK);

        // 4. Map to DTOs
        var searchResult = new SearchResultDto
        {
            Results = results.Select(r => new SearchResultItem
            {
                DocumentId = r.DocumentId,
                Title = r.DocumentTitle,
                Snippet = HighlightText(r.Content, request.QueryText),
                SimilarityScore = r.Similarity,
                Source = r.Filename,
                PageNumber = r.PageNumber
            }).ToList(),
            TotalResults = results.Count,
            QueryTime = stopwatch.ElapsedMilliseconds,
            FromCache = false
        };

        // 5. Cache results (5 minutes TTL)
        await _cacheService.SetAsync(cacheKey, searchResult, TimeSpan.FromMinutes(5));

        return Result<SearchResultDto>.Success(searchResult);
    }
}

## 4. Cấu trúc Modular Monolith

### 4.1 Nguyên tắc thiết kế Modular Monolith

Modular Monolith là kiến trúc trung gian giữa Monolith và Microservices, cho phép:

- **Tách biệt modules**: Mỗi module có cấu trúc độc lập, có bounded context riêng
- **Giao tiếp rõ ràng**: Modules giao tiếp qua well-defined interfaces (MediatR)
- **Dễ dàng tách thành Microservices**: Khi cần, có thể extract module thành service riêng
- **Shared Kernel**: Các common components được chia sẻ một cách có kiểm soát

#### 5.2.2 Database: PostgreSQL + pgvector

**Tại sao không dùng dedicated Vector DB?**

| Vector DB | Pros | Cons |
|-----------|------|------|
| **Pinecone** | Managed, scalable | Cost, vendor lock-in, latency |
| **Weaviate** | Graph + Vector | Complex setup, memory heavy |
| **Qdrant** | Rust-based, fast | Newer, smaller community |
| **pgvector** | Single DB, ACID, simple | Limited horizontal scaling |

**pgvector Advantages:**
1. **Single database**: Không cần maintain riêng vector DB
2. **ACID transactions**: Consistency với main data
3. **Easy backup**: Single backup cho cả data + vectors
4. **No sync needed**: Data và vectors luôn in-sync
5. **Sufficient scale**: Đủ cho hầu hết enterprise use cases (< 10M vectors)

**pgvector Index Configuration:**
```sql
-- HNSW index for approximate nearest neighbor search
CREATE INDEX idx_chunks_embedding_hnsw 
ON document_chunks 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- Alternative: IVFFlat index (faster build, slower query)
CREATE INDEX idx_chunks_embedding_ivfflat 
ON document_chunks 
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);
```

### 6.1 RAG Pipeline Chi tiết

**Retrieval-Augmented Generation (RAG)** là kỹ thuật kết hợp retrieval (tìm kiếm) với generation (sinh text) để tạo câu trả lời chính xác dựa trên tài liệu.

```
┌────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                             RAG PIPELINE OVERVIEW                                                   │
│                                                                                                                    │
│    User Query                                                                                                      │
│        │                                                                                                           │
│        ▼                                                                                                           │
│  ┌─────────────┐                                                                                                   │
│  │   RETRIEVE  │  1. Embed query → vector                                                                         │
│  │             │  2. Search vector DB → relevant chunks                                                           │
│  │             │  3. Return top-k most similar chunks                                                             │
│  └──────┬──────┘                                                                                                   │
│         │                                                                                                          │
│         ▼                                                                                                          │
│  ┌─────────────┐                                                                                                   │
│  │  AUGMENT    │  4. Combine retrieved chunks with prompt template                                                 │
│  │             │  5. Add system instructions, context                                                               │
│  │             │  6. Build final prompt                                                                            │
│  └──────┬──────┘                                                                                                   │
│         │                                                                                                          │
│         ▼                                                                                                          │
│  ┌─────────────┐                                                                                                   │
│  │  GENERATE   │  7. Call LLM (GPT-4o / llama3)                                                                   │
│  │             │  8. Generate response based on context                                                          │
│  │             │  9. Stream response to user (optional)                                                            │
│  └─────────────┘                                                                                                   │
│                                                                                                                    │
│  ┌────────────────────────────────────────────────────────────────────────────────────────────────────────────┐   │
│  │                                    WHY RAG?                                                                    │   │
│  │                                                                                                             │   │
│  │  Without RAG:                                                                                                │   │
│  │  • LLM relies on training data (may be outdated, inaccurate)                                                  │   │
│  │  • May hallucinate (generate plausible but false information)                                                 │   │
│  │  • No access to internal/private documents                                                                    │   │
│  │                                                                                                             │   │
│  │  With RAG:                                                                                                    │   │
│  │  ✓ LLM answers based on retrieved documents (grounded)                                                        │   │
│  │  ✓ Reduces hallucinations (cited sources)                                                                   │   │
│  │  ✓ Access to latest internal documents                                                                        │   │
│  │  ✓ Cost-effective (no fine-tuning needed)                                                                   │   │
│  │  ✓ Traceable (know which documents were used)                                                               │   │
│  └────────────────────────────────────────────────────────────────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 6.3 Advanced RAG Strategies

```
┌────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                    ADVANCED RAG STRATEGIES                                                          │
│                                                                                                                    │
│  ┌────────────────────────────────────────────────────────────────────────────────────────────────────────────┐   │
│  │  1. HYBRID SEARCH (Vector + Keyword)                                                                       │   │
│  │                                                                                                             │   │
│  │  Combines semantic similarity with keyword matching:                                                         │   │
│  │                                                                                                             │   │
│  │  final_score = α × vector_similarity + (1-α) × bm25_score                                                  │   │
│  │                                                                                                             │   │
│  │  • α = 0.7 (weight vector search higher)                                                                   │   │
│  │  • Benefits: Catches exact keyword matches + semantic meaning                                             │   │
│  └────────────────────────────────────────────────────────────────────────────────────────────────────────────┘   │
│                                                                                                                    │
│  ┌────────────────────────────────────────────────────────────────────────────────────────────────────────────┐   │
│  │  2. RERANKING (Cross-Encoder)                                                                              │   │
│  │                                                                                                             │   │
│  │  Two-stage retrieval:                                                                                      │   │
│  │  1. Fast vector search → top 50 candidates                                                                │   │
│  │  2. Cross-Encoder reranking → top 10 final results                                                         │   │
│  │                                                                                                             │   │
│  │  Cross-Encoder: More accurate but slower (used only on candidates)                                         │   │
│  └────────────────────────────────────────────────────────────────────────────────────────────────────────────┘   │
│                                                                                                                    │
│  ┌────────────────────────────────────────────────────────────────────────────────────────────────────────────┐   │
│  │  3. MMR (Maximum Marginal Relevance)                                                                        │   │
│  │                                                                                                             │   │
│  │  Diversifies results to avoid redundancy:                                                                  │   │
│  │                                                                                                             │   │
│  │  MMR = argmax [λ × Sim(query, doc) - (1-λ) × max(Sim(doc_i, doc_j))]                                      │   │
│  │                                                                                                             │   │
│  │  • λ = 0.7 (relevance vs diversity tradeoff)                                                              │   │
│  │  • Prevents getting multiple chunks from same document                                                     │   │
│  └────────────────────────────────────────────────────────────────────────────────────────────────────────────┘   │
│                                                                                                                    │
│  ┌────────────────────────────────────────────────────────────────────────────────────────────────────────────┐   │
│  │  4. QUERY EXPANSION / REWRITING                                                                            │   │
│  │                                                                                                             │   │
│  │  Before embedding generation:                                                                               │   │
│  │  • HyDE (Hypothetical Document Embeddings): Generate hypothetical answer, embed it                        │   │
│  │  • Query decomposition: Break complex questions into sub-queries                                           │   │
│  │  • Synonym expansion: Add related terms for better coverage                                               │   │
│  └────────────────────────────────────────────────────────────────────────────────────────────────────────────┘   │
│                                                                                                                    │
│  ┌────────────────────────────────────────────────────────────────────────────────────────────────────────────┐   │
│  │  5. PARALLEL QUERY (Query Decomposition)                                                                   │   │
│  │                                                                                                             │   │
│  │  Complex question → Multiple simple queries → Combine results                                             │   │
│  │                                                                                                             │   │
│  │  Example: "So sánh chính sách nghỉ phép của công ty A và B?"                                                │   │
│  │  → Query 1: "Chính sách nghỉ phép công ty A"                                                              │   │
│  │  → Query 2: "Chính sách nghỉ phép công ty B"                                                              │   │
│  │  → Combine and compare                                                                                      │   │
│  └────────────────────────────────────────────────────────────────────────────────────────────────────────────┘   │
│                                                                                                                    │
│  ┌────────────────────────────────────────────────────────────────────────────────────────────────────────────┐   │
│  │  6. CONTEXTUAL COMPRESSION                                                                                 │   │
│  │                                                                                                             │   │
│  │  After retrieval, compress chunks to keep only relevant parts:                                              │   │
│  │  • LLM-based summarization of each chunk                                                                   │   │
│  │  • Remove redundant/irrelevant sentences                                                                   │   │
│  │  • Preserve key information (facts, numbers, names)                                                        │   │
│  │  • Reduces token usage in final prompt                                                                      │   │
│  └────────────────────────────────────────────────────────────────────────────────────────────────────────────┘   │
│                                                                                                                    │
│  ┌────────────────────────────────────────────────────────────────────────────────────────────────────────────┐   │
│  │  7. CITATION/GROUNDING                                                                                     │   │
│  │                                                                                                             │   │
│  │  After generation, add source citations:                                                                     │   │
│  │                                                                                                             │   │
│  │  1. Identify which retrieved chunks were used                                                               │   │
│  │  2. Extract source metadata (filename, page)                                                               │   │
│  │  3. Attach citations to response                                                                           │   │
│  │  4. Enable "jump to source" functionality                                                                  │   │
│  └────────────────────────────────────────────────────────────────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

## 12. Performance Considerations

### 12.1 Vector Search Optimization

```sql
-- pgvector Index Selection Guide

-- HNSW Index (Recommended for most use cases)
-- Pros: Fast query time, good recall
-- Cons: Slower build, higher memory usage

CREATE INDEX idx_chunks_embedding_hnsw 
ON document_chunks 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- Parameters:
-- m: Number of bi-directional links (16-64, higher = better recall, more memory)
-- ef_construction: Size of dynamic candidate list (64-400, higher = better recall, slower build)

-- IVFFlat Index (Good for large datasets, pre-clustering)
-- Pros: Faster build, lower memory
-- Cons: Slower query, lower recall

CREATE INDEX idx_chunks_embedding_ivfflat 
ON document_chunks 
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);

-- Parameters:
-- lists: Number of clusters (dataset size / expected results per cluster)

-- Query with different similarity metrics
SELECT 
    content,
    -- Cosine distance (default, recommended)
    1 - (embedding <=> '[0.1, 0.2, ...]'::vector) AS cosine_similarity,
    -- Euclidean distance
    embedding <-> '[0.1, 0.2, ...]'::vector AS euclidean_distance,
    -- Negative inner product (for normalized vectors, equivalent to cosine)
    -1 * (embedding <+> '[0.1, 0.2, ...]'::vector) AS inner_product
FROM document_chunks
ORDER BY embedding <=> '[0.1, 0.2, ...]'::vector
LIMIT 10;
```

## 13. Kết luận

### 13.1 Tổng kết Kiến trúc

Hệ thống Document Q&A với RAG được thiết kế theo nguyên tắc **Clean Architecture + CQRS + Modular Monolith**:

1. **Clean Architecture**: Đảm bảo separation of concerns, testability, và maintainability
2. **CQRS**: Tối ưu cho read-heavy workload của semantic search
3. **Modular Monolith**: Dễ phát triển ban đầu, có thể tách thành microservices khi cần

### 13.2 Các điểm mạnh

- **Scalability**: Horizontal scaling với K8s, vector search với pgvector HNSW
- **Performance**: Multi-level caching, async processing, streaming responses
- **Security**: JWT + RBAC, input validation, rate limiting
- **Observability**: Structured logging, metrics, distributed tracing
- **AI Integration**: Flexible AI provider selection (OpenAI/Ollama)
- **Data Privacy**: Multiple options for sensitive data handling

### 13.3 Areas for Future Enhancement

- **Multi-tenancy**: Support multiple organizations with data isolation
- **Real-time Collaboration**: WebSocket-based multi-user chat
- **Advanced RAG**: HyDE, query decomposition, agentic RAG
- **Fine-tuning**: Custom embedding/LLM models for domain-specific terms
- **Graph Database**: Neo4j for relationship-aware retrieval
- **Microservices**: Extract heavy components (worker, AI) to separate services
